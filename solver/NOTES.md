**单例模式（服务端 `POST /api/runs` B 式的逐用例调用）**

```bash

```

- `argv[1]` = 输入路径、`argv[2]` = 输出路径；映射写文件**并且**原样打到 stdout（服务端没

## 3. 算法（报告 §2 的复原）

```
for P in 合法专家并行度（P∣E、P∣R、P∣S 或 S∣P）:
    MAP = best_placement(P)         # 逐层：LPT / 顺序 / 换位下降，取 m_l 最小
    逐层时长 = formula.compute_layer_quantities(...)     # 自算 m/x/durations
    for V in divisors(R/P) 且 V ≤ L:
        D = R/(P·V)
        for ψ in psi_candidates(L, V, ΣC, ΣWc):
            若任一 stage 的 Mexp > M：丢弃
            lb = max_v nmb·max(ΣC_v, ΣWc_v)
按 lb 升序评估每个 (P,V,ψ)：
    for W in 窗口候选（nmb…1）:
        for 变体（fwd/back 优先 × mb、ℓ 升降序 × mb-major/ℓ-major）:
            sched = 事件驱动贪心列表调度（依赖就绪 + 引擎空闲 + 窗口 W）
            Time 严格优于当前最优时才做内存核算 → 更新
在最优配置上：引擎序列局部搜索（模拟退火，多种子）
（可选，`--exact`）再对 nmb=2 且每 stage 单层的形状做精确搜索：通信交错穷举 + 计算顺序线性扩展（§9）
```

### 3.1 调度器要点（和题面 §4.2 的对应）

- **依赖**：`s→disp→gemm→comb`；`s_bwd→comb_bwd→gemm_dx→disp_bwd`；`gemm_dw` / `s_dw` 只跟
  `comb_bwd`；`s(ℓ) ≥ comb(ℓ−1)`；`s_bwd(ℓ) ≥ disp_bwd(ℓ+1)`（且 ≥ 本层 `comb`）。
- **引擎互斥**：每个卡组一套计算/通信引擎；**非零时长操作才占用**（零时长操作照常输出，
  但不挡引擎）；相等时刻释放。
- **窗口 W**：`mb` 在某卡组首层的前向要等 `mb−W` 在该卡组的反向全部完成。它只是求解器侧
  的 1F1B 启发式（评测器不强制），用来压住同时活跃的 `(mb,层)` 数。
- **出堆模式**：`prio`（按优先级，报告 §2.4）与 `early`（按最早可开始时刻，堆键惰性修正）。
- **左移压实**：按拓扑序把每个操作移到最早可行时刻（纯改进，`Time` 单调不增）。
- **引擎序列退火**：把调度看成「每个卡组每套引擎上的一个操作序列」，随机交换两条序列上的
  操作并按「依赖 + 序列顺序」求最长路，模拟退火。贪心只能换拓扑，这一步才把 ex2 / ex6 / ex5
  从 4928 / 1752 / 448 压到 4880 / 1744 / 416。复杂度 `O(n + 边数)`/次，小用例每秒十万次。

### 3.2 剪枝与预算（10 s 硬约束）

- `Mexp > M` 的配置直接丢弃；按 `lb` 升序评估，`lb ≥ best.time` 立即整体停止；
- 只在 `Time` 严格改进时才做内存核算（报告 §4 第 23 条的 fast_eval 思路）；
- **实测单次调度耗时**用于预算判断（大用例一次 640k 条调度约 1.2 s，不能撞穿 10 s）；
- 最终「内存核算 + 渲染落盘」预留 `0.25 s + 1 µs/op`；搜索用剩余预算，局部搜索最多再用
  `min(4 s, budget/2)`；
- 搜索被截断时返回**当前最好的合法解**；若主搜索一无所获，回退到「小窗口 + 全变体」重扫。

## 5.5 大用例（>12 万条 op）的两个关键决定

1. **`early` 出堆**：`prio` 按 `(方向, mb, 层)` 排序，窗口一旦被内存压小，前向会先挤成一批、
   反向再挤成一批，64 个卡组的并行度掉到 2 个（实测 3.16 % 利用率、慢 29 倍）。只在
   "`_window_cap < nmb`（窗口确实被压小）"时优先用 `early`；否则 `prio` 已经够好，
   而 `early` 在 64 万条 op 上单次就要 5 s，无差别使用会把预算烧光。
2. **窗口候选不能逐个枚举**：`nmb > 64` 时改用对数刻度（否则 `nmb=1000` 会有 1000 个候选），
   并先做 3 次"窗口探测"（`nmb`、`nmb/8`、`nmb/32`，**按升序**跑，小窗口更便宜），
   再回到最好的窗口扫变体。b11 因此从 1.26×lb 降到 **1.00×lb**，总耗时 7.0 s → 4.0 s。

回归测试见 `solver/selftests/test_tight_window.py`（7 条）。

### 6.1 "三段相加"的下界不能用（方法论修正）

本节之前给出的 `有效下界 = 头段 + 引擎工作量 + 尾段` **不能三段直接相加**：尾段里的
`comb_bwd` / `disp_bwd` 本身就是通信工作量里的操作，相加会把同一段算两遍（ex2 重复 800）。

后果不是"数字不好看"，而是**结论可能是错的**：一个偏大的数不再是合法下界，用它和本解比较
会得出"已证明最优"或"还有空间"的错误判断。

正确用法：

- 下界只按**单一来源**取（`max(引擎工作量, 链头 + 工作量, …)`），不跨来源求和；
- `Time == 下界` 只有在"下界确实只来自一个来源"时才能当最优性证明（ex3/ex4 就是这种）；
- 真正的最优性判定交给 CP-SAT（ex1/ex2/ex5/ex6 都已用它确认）。

### 6.2 单来源下界（可用的那部分）

题面 §4.2 第 3 条的引擎工作量下界 `lb = max_v nmb·max(ΣC_v, ΣWc_v)` 是对的但偏松。可以安全
补强的是**只来自单一来源**的那一项：

| 用例 | lb | 可补强的单一来源 | 结论 |
| --- | --- | --- | --- |
| ex3 | 4000 | 通信工作量 8×500 | 下界 = 本解，**证明最优** |
| ex4 | 3200 | 通信工作量 8×400 | 下界 = 本解，**证明最优** |
| ex1 | 560 | 首个 `disp` 必等 `s` 的 16 ⇒ 16 + 560 = 576 | 下界 = 本解，**证明最优** |
| ex2 / ex5 / ex6 | — | 需要同时计入"链头"和"链尾回落"，两者跨越通信工作量，**不能相加** | 交给 CP-SAT 判定（§6） |

示例：ex2 的 `3200` 是卡组 1 通信引擎的**全部**工作量（8 个 400 的通信操作），而"尾段回落"
里的 `comb_bwd 400 + disp_bwd 400` **就是这 8 个操作中的两个**。把两者相加等于重复计入 800，
得到的数不再是合法下界（真实最优可能比它小），因此不能用它宣称任何结论。

## 7. 输出格式（题面 §3 / CONTRACT §6）

- `V P` 一行（2026-10 版取消 D）；`PSI` 行先写块数 `K` 再写 `K−1` 个切点；**`K=1` 时只写 `1`**（空切点，
  ex1/ex3/ex4/mini 都是这种形态）；
- `MAP` 共 `L` 行，每行 `E` 个整数，取值 `[0,P)` 且**每个 rank 恰好 `E/P` 个**（LPT 带容量约束）；
- `SCHEDULE` 每行 `t mb:ℓ:op …`，`t` 非降；**同一时刻的多个操作合并在同一行**（ex5 的
  `128 0:1:comb 0:1:s_bwd 1:0:comb` 这种）；
- **零时长操作照常输出**（`x=0`、`Fs=0`、`αβ=0` 时大量出现），评测器按题面 §4.1/§4.2 认定为
  不占引擎；
- 本求解器只产 `K=V`（每卡组一块）；`K=2V`（DualPipe 镜像配对）是合法但未使用的自由度。

## 8. 已知限制 / 可改进

1. **没有 `K=2V`（DualPipe）**：需要把两块映射到同一卡组并共用一对引擎，收益集中在
   `V` 较小、`nmb` 较大的形状；六个样例用不到，未实现。
2. **局部搜索只对小用例开启**（`n_ops ≤ 20000`，因为单次求值 `O(n)`）；大用例靠贪心 + 多
   配置。若大用例是 `nmb=2` 的小层数形状，仍会命中。
3. **MAP 只做 LPT + 换位下降**：报告说 `E/P ≥ 3` 且极偏斜时 LPT 可能次优；本实现有逐层换位
   下降（`E ≤ 48` 时），但没做枚举。
4. **ψ 候选集是启发式的**：`dp_split2` + 均分 ±1；没有对切分做局部搜索（报告 §4 第 11 条对
   大用例做过扰动搜索，无收益）。
5. **报告目标不可达**（§6 / CONTRACT §7.1）：4040 / 384 / 1460 低于有效下界 4832 / 416 / 1736，
   在题面模型下不可能达到；剩余空间只有 ex2 ≤ 48、ex6 ≤ 8（可达性未证）。
6. **精确搜索的覆盖仍不完整**（§9）：通信交错穷举了（4900 对），计算顺序只对第一阶段最好的
   4 个通信交错做线性扩展枚举；完整联合枚举 ≈ 3.1×10^7（ex2），10 s 预算内跑不完。`--exact`
   默认关闭，默认输出与之前逐字节相同。

## 9. 精确搜索（`--exact`，t11）

**定位**：主搜索（网格枚举 + 贪心 + 序列退火）之后的**可选**第二阶段，只对「`nmb=2` 且每个
stage 只含 1 层」的形状生效（ex1–ex6 都命中；`L ≥ 3` 的多 stage 形状交错数爆炸，直接不适用）。
**默认关闭**：不带 `--exact` 时输出与之前逐字节相同（对 `out/ex*.out`、`out/mini.out` 逐个
`cmp` 验证过）。

### 9.1 方法

给定「每个卡组两套引擎上的操作序列」，按最早可开始放置就得到该序列下 makespan 最小的调度，
所以**穷举这些序列**就覆盖了该网格/切层/MAP 下的最优解。本模块枚举：

* **通信引擎**：同一 `(mb, 层)` 的通信操作依赖顺序固定 `disp → comb → comb_bwd → disp_bwd`
  （中间隔着计算引擎上的 `gemm` / `gemm_dx`），于是每个 stage 只有两条 mb 链的**交错**自由，
  `C(4+4,4) = 70` 种；两个 stage 的笛卡尔积 = **4900 对**（其中 2554 对能排出合法调度，其余
  会因为跨 stage feed 与引擎序列互相卡死，模拟器直接判不可行并跳过）；
* **计算引擎**：第一阶段用 4 个优先级变体做「最早可开始 + 固定优先级」贪心；第二阶段枚举计算
  操作的**线性扩展**（偏序取经通信传递出的 `gemm < gemm_dx`、`gemm < gemm_dw` 等）：
  ex2 每 stage 80 个（两 stage 全枚举 6400 对），ex6 每 stage 33 264 个（超过
  `COMP_EXTENSION_CAP = 40000` 或笛卡尔积超过 `COMP_PAIR_CAP` 就改为逐 stage 枚举）。

跨 stage 的两条 feed（`s(mb,ℓ+1) ≥ comb(mb,ℓ)`、`s_bwd(mb,ℓ) ≥ disp_bwd(mb,ℓ+1)`）在模拟里
自然满足；生成的调度构造上满足题面 §4.2，**最终合法性仍以 judge 判定为准**（`--check` 逐例
复核）。全过程无随机数，同一输入两次运行结果相同。

| ex1 | 70 | 70 | 60 280 | 1.4 s | 576（= 有效下界，无改进） |
| ex2 | 4900 | 2554 | 45 200 | 1.9 s | **4880（无改进）** |
| ex3 | 70 | 70 | 304 | 0.01 s | 4000（= 有效下界） |
| ex4 | 70 | 70 | 600 | 0.02 s | 3200（= 有效下界） |
| ex5 | 1（P=1，通信全零时长） | 1 | 60 004 | 5.7 s | 416（= 有效下界） |
| ex6 | 4900 | 2554 | 79 600 | 3.7 s | **1744（无改进）** |

`--exact` 开启后单例墙钟：ex1 ≈2.4 s、ex2 ≈2.6 s、ex3/ex4 ≈0.02 s、ex5 ≈6.1 s、ex6 ≈4.5 s，
全部在 10 s 硬上限内（默认路径 0.00–0.88 s 不变）。模拟次数由 `PHASE_B_BUDGET = 60000` 等
上限**写死**，与机器快慢无关；耗时随机器浮动 ±10% 左右。

**结论：10s 预算内未找到更优解。** ex2 仍为 4880（距有效下界 4832 差 48），ex6 仍为 1744
（距 1736 差 8），ex5 的 416 已等于有效下界。**这不构成「不可达」的证明**：可达性仍未证——
通信交错是穷举完了，但计算顺序只对第一阶段最好的 4 个通信交错做了线性扩展枚举；完整的联合
枚举是 4900 × 6400 ≈ 3.1×10^7（ex2），受 10 s 预算限制没有跑完。

### 9.3 额外的离线证据（不计入单例预算，仅用于判断是否值得再投入）

* **全 comm × 采样 comp 扫描**：2554 个可行通信交错 × 400 组计算顺序（固定种子采样）=
  每例 1 021 600 次模拟；ex2 用 35.8 s、ex6 用 24.2 s，**最好仍是 4880 / 1744**；
* ex2：第一阶段最好的 30 个通信交错 × 全部 6400 个计算顺序对 = 192 000 次模拟，最好仍是 4880；
* ex6：最好通信交错下分别枚举两个 stage 的 33 264 个计算线性扩展（66 528 次），最好仍是 1744；
* 两者都做过「计算顺序爬山」（交换邻域、多起点），仍停在 4880 / 1744；
* 结论：在这套「引擎序列 + 最早开始」的表述里没有找到 48 / 8 的回收路径；若有效下界本身不紧，
  这段间隙可能根本不存在。**未证明不可达**，只是 10 s 内没搜到。
