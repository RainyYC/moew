# 大样例：11 个用例 + 求解器在最大规模上的三个缺陷

> 官方 6 个样例被刻意压到可手算（`R≤4, L≤2, E≤4, nmb=2`，**最多 40 条 op**）。题面 §7 自己说："样例的规模压到了可以手算……样例也不代表测试点的规模与难度"。
> 本文用题面 §6 的上限造了 11 个大用例（最多 **64 万条 op**），并记录实测。

## 1. 规模对照

| | R | L | E | nmb | ops |
| --- | --- | --- | --- | --- | --- |
| 官方样例（6 个） | 2–4 | 1–2 | 2–4 | 2 | **20–40** |
| 题面 §6 上限 | 512 | 64 | 512 | 10³ | **640 000** |
| 本电池 | 64–512 | 4–64 | 4–512 | 102–1000 | 40 000–640 000 |

生成：`python3 tools/gen_battery.py`（每组只变一个维度，清单见 `bigcases/battery/MANIFEST.md`）。

## 2. 实测（4 核 / 16 GiB，Python 3.14，自动预算）

> **2026-10 版的影响**：取消 `D` 后 `V·P=R`，而切点规则要求 `V≤L`，于是 `P ≥ R/L`。
> 这批用例是 `R=512, L=64`，因此 `P` 被迫 **≥ 8**（旧版可以取 `P=1`）。通信量随之变大，
> `lb` 也变大：例如 b05 的 `lb` 从 4.8e13 涨到 5.7e15，但 `Time/lb` 仍只有 1.06。
> 也就是说**新规则让"小 P 大模型"这条廉价退路消失了**，这对所有参赛者一样。

所有用例都在 10 s 时限内（最慢 6.2 s），且全部经判题器判定合法。最差比值 1.62（b02–b04），
它是 `(nmb+V-1)/nmb = 165/102` 的流水线填充代价，属结构性下限（见 §3.2）。

`lb` 是题面 §4.2 第 3 条的引擎工作量下界（单来源，合法但偏松）。

## 3. 三个缺陷（按严重度）

### 3.1 【已修】回退路径没有预算约束 → 挂死

`nmb=1000` + `M=256MiB` 的 b06 原先**永远不返回**（实测 >60 s，被 `timeout` 杀掉）：

1. 主搜索在 5 s 预算内，每个 `W` 都先试 3 个变体 × 1.25 s，钱全花在必然超内存的 `W=nmb` 上；
2. 找不到合法解 → 进回退分支，而**回退循环没有任何时间检查**，configs × windows × modes × variants × 3 个 gap 无限扫下去。

判题时限 10 s，所以这是**必然 0 分**。

已修两处（`solver/solve.py`）：
- 回退分支加 `fallback_deadline`，到点返回当前最好解；
- `_try_config` 增加 `_window_cap()`：按 `Mact` 余量算出窗口上限，先把必然超内存的 `W` 剪掉；同一 `W` 连续 2 次内存非法就换下一个 `W`。

修复后 b06 3.7 s 返回合法解。

### 3.2 【已修】内存逼小窗口时，调度器退化 30 倍 → 现在 1.09

b06 / b10 曾经是 32–35 倍。定位链条（每一步都实测过）：

| 观测 | 数值 |
| --- | --- |
| 逐卡组利用率 | 卡组 0 忙 4.94e15，却横跨 0..1.57e17 → **3.16 %** |
| 去掉窗口门控 | Time **5.23e15（快 30 倍）**，但 `Mact` 超内存 |
| 换 8 个优先级变体 | 全部 1.57e17–3.16e17，不是变体问题 |
| 窗口释放改 `s_bwd` 排上 | 只快 0.8 % |
| **改 `early` 出堆（按最早可开始时间）** | **5.38e15，内存合法** ✅ |

根因：`prio` 出堆按 `(方向, mb, 层)` 排序，窗口一被压小，所有前向会先挤成一批、反向再挤成
一批（`fwd_first=True` 让全部前向的优先级都高于反向），64 个卡组于是只有约 2 个在同时干活。
`early` 按时间推进，天然保持交错。

实现要点（`solver/solve.py`）：

```python
cap_now = _window_cap(case, plan)              # 按 Mact 余量算窗口上限
capped = cap_now is not None and cap_now < case.nmb
modes = ("early", "prio") if (not big or capped) else ("prio", "early")
```

只在"窗口确实被压小"时才优先 `early`——它在 64 万条 op 上单次要 5 s，无差别使用会把预算烧光
（b05 曾因此从 3.4 s 涨到 7.8 s 而质量不变）。

结果：b06 **32.4 → 1.09**，b10 **34.6 → 1.19**。

### 3.2b 【已修】窗口候选被逐个枚举，够不到好窗口

`window_candidates` 在非 big 分支里返回 `range(nmb, 0, -1)`——官方样例 `nmb=2` 时无所谓，
但 b11（`nmb=1000`）会生成 **1000 个候选**，预算全花在 `W≈nmb` 上。

同时 log 刻度里 `W≈nmb/8` 才是好窗口：b11 在 `W=125` 时是 **1.00×lb**，而 `W=1000` 只有 1.26×lb。

修法两处：
1. `nmb > 64` 时改用对数刻度（候选 ≤ 32 个）；
2 中等规模用例先做 3 次"窗口探测"（`nmb`、`nmb/8`、`nmb/32`），**按窗口升序**跑（小窗口更便宜），
   再回到最好的窗口上扫变体。

结果：b11 **1.26 → 1.00**，且总耗时从 7.0 s 降到 4.0 s。

### 3.3 【已改】窗口释放按"激活存活"而非"反向全完成"

原先 `bw_left` 计 6 个反向操作，要等 `gemm_dw`/`s_dw`（旁支、优先级最低）也排上才放行下一个
mb；现在按 `s_bwd` 计入，语义上更贴合 `Mact` 的定义（§4.6：激活从 `comb` 结束到 `s_bwd` 开始存活）。
单独收益约 0.8 %，但让语义与内存核算一致，是 §3.2 修复的前提。

## 4. 结论

- **大样例确实存在，而且按上限造**：64 万条 op、R=512、L=64、E=512。
- **全部 11 例都在 10 s 内出合法解**（最慢 6.2 s），`Time/lb` 最差 1.62。
- **内存宽松的大用例贴着物理极限**：1.04–1.07（瓶颈引擎 94–96 % 利用率）。
- **`nmb` 小 + `V=64` 的 1.41–1.62 是结构性的**：`(nmb+V-1)/nmb = 165/102`，且 `V` 越大越好（单调），已是最优选择。
- **修掉了两个真实的坑**：回退路径无预算（必然 0 分）、内存压窗口时退化 30 倍。
- **剩下的差距都在 1.0–1.25**，其中 b08 的 1.25 经穷举确认就是该实例的最好值（不是搜索不足）。

## 6. 随机压力测试（fuzz）：34 个随机用例

`tools/fuzz.py` 在题面 §6 的范围内随机造用例（随机 `N/S/L/E/k/nmb/Z/M/Bin/Bout/U/Uact/d/b`，
逐层随机偏斜），检查三件事：**是否超时、是否合法、离下界多远**。

| 轮次 | 用例数 | 超时 | 非法 | 无解（其实有解） | 修复后 |
| --- | --- | --- | --- | --- | --- |
| seed 1–4 | 34 | 0 | 0 | **2** | 1 例真不可行、1 例已修 |
| seed 5–7 | 18 | 0 | 0 | 0 | — |

两个"无解"里：

- 一个是**真不可行**：`Uact = 262144 > M = 1805`，任何调度都至少有一份激活存活，必然超内存。
  求解器返回"没有合法映射"（退出码 1）是正确行为。
- 另一个是**求解器的漏洞**：`gap=0` 下所有调度都超内存，只有给通信引擎插 1 个时间单位空隙才
  压得住峰值。而"插空隙救援"当时只写在回退分支里，回退又只剩零点几秒 → 返回无解 → **该测试点
  0 分**。已修：把 `comm_gap ∈ {0,1,2,4,8}` 放进主搜索的非法分支（内层循环），一发现超内存
  就先试插空隙。

**"差距大"的 5 例全部是 `nmb` 很小（2–8）而 `L` 很大（32–64）**：此时 `lb` 只算单卡组的引擎
工作量，而实际上 `nmb` 个 microbatch 填不满 `V=64` 级流水线。例：`nmb=4, L=64` 的
`Time/lb=4.10`，但理论下限是 `64t/4 = 16t`（4 个 mb 最多让 4 个 stage 并行），而 `lb = 4t`——
所以 4.10 实际是**真下限的 1.02 倍**。这类"差距"是 `lb` 不紧，不是求解器不行。
