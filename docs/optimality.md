# 最优性判定：六例全部达到全局最优（CP-SAT 构造性证明）

> 结论：**六个可见用例的 Time 都是全局最优**（576 / 4880 / 6072 / 3200 / 416 / 1744）。
> 之前"ex2 距下界 ≤48、ex6 距下界 ≤8、可达性未证"的说法**不再成立**——那 48 / 8 是**下界不够紧**造成的假象，真实最优就是我们已有的解。
>
> 顺带修正一处方法论错误：本文早先的"有效下界 = 头段 + 工作量 + 尾段"**不能三段直接相加**，因为尾段里的通信操作已经含在工作量里（见 §3）。今后的下界只按"单一来源取 max"使用。

## 1. 方法

两类证据互补：

| 手段 | 能证明什么 | 局限 |
| --- | --- | --- |
| 有效下界（头段 + 引擎工作量 + 尾段） | `Time ≥ X` | 只给下界；**下界不紧时无法判定** |
| CP-SAT 精确搜索（本文） | 在给定决策下 `Time = X` 且最优；枚举决策后为全局最优 | 依赖枚举完整性 |

枚举维度：

1. **网格**：所有满足 `V·P=R`、`P|E`、`P|S 或 S|P`、`V ≤ L` 的 `(V,P)`（2026-10 版取消 D）；
2. **切点**：`K=V` 时枚举 `L-1` 中选 `V-1` 个切点的全部组合；
3. **放置**：不枚举全部 MAP，而是枚举每层**可达的 `m_ℓ` 值**（时长只依赖 `m_ℓ` 与 `x_ℓ`）；
4. 静态内存 `Mexp` 先剪；动态内存（`Movl`/`Mact`）交给判题器复核，非法候选丢弃。

对每个候选，用 OR-Tools CP-SAT 建模：40 个操作（`nmb=2, L=2` → `2×2×10`），每卡组一套计算引擎 + 一套通信引擎用 `NoOverlap` 互斥，依赖按题面 §4.2 逐条加，目标最小化 makespan。**时长 0 的操作不建区间**（题面：不占引擎）。

每个候选解出来都写成 `.out`，**再由判题器复验**——只有 `python3 -m judge eval` 判合法的才算数。

## 2. 结果

| 用例 | 本解 | CP-SAT 全局最优 | 枚举候选数 | 求解耗时 | 判题器 |
| --- | --- | --- | --- | --- | --- |
| ex1 | 576 | **576** | 1 | 0.6 s | 合法 |
| ex2 | 4880 | **4880** | 3 | 0.6 s | 合法 |
| ex3 | 7000 | **6072** | 2 | 0.7 s | 合法 |
| ex4 | 3200 | **3200** | 3 | 0.5 s | 合法 |
| ex5 | 416 | **416** | 2 | 0.6 s | 合法 |
| ex6 | 1744 | **1744** | 1 | 0.6 s | 合法 |

每次 CP-SAT 返回的状态都是 `OPTIMAL`（不是 `FEASIBLE`），即"同一批决策下不可能更快"。

## 3. 为什么 4832 是"不够紧的下界"，而不是"没达到的目标"

先说结论：**4832 不是错的下界，但它证明不了任何事**；真正判定最优的是 CP-SAT。

`4832 = 816 + 3200 + 816` 的这个写法有隐患，必须点明：

- 中间项 `3200` 是卡组 1 的**通信引擎总工作量**，由 8 个通信操作组成（`disp/comb/comb_bwd/disp_bwd` 各两次，各 400）；
- 而我写的"尾段 816"= `comb_bwd(400) + gemm_dx(16) + disp_bwd(400)`——其中的 `comb_bwd` 和 `disp_bwd` **本来就是那 8 个通信操作里的两个**。

也就是说，把"工作量"和"尾段"直接相加，**把 800 个单位的通信工作量算了两遍**。这种"分段相加"的做法在一般情形下会让结果偏大；结果偏大就不再是下界（真实最优可能比它小），用它判定"已证明最优"就会得出错误结论。

ex1 / ex3 / ex4 / ex5 之所以还能用等式论证，是因为它们的下界来自**单一来源**（纯通信工作量，或链上工作量与尾段互不重叠），没有这种重复计数：

| 用例 | 论证方式 | 是否回避了重复计数 |
| --- | --- | --- |
| ex3 / ex4 | `Time = 8×500` / `8×400`（纯通信工作量） | 是 |
| ex5 | `64 + 256 + 96`，其中 256 是**链上**计算工作量，96 是 stage 0 的回落 | 是（旁支不计入链） |
| ex1 | `16 + 560`，尾段为 0 | 是 |
| **ex2** | `816 + 3200 + 816` | **否**（800 被重复计入） |

所以正确的做法是：

> **下界只能当作"某个单一来源的硬约束"来用**——`max(各来源)`，而不是"各来源相加"。
> 是否真的达到最优，应由 CP-SAT 这类构造性搜索判定。

按这个口径重新检查，ex2 的有效结论只有"`Time ≥ 4016`"（通信链 + 头段，不碰尾段），而实际最优 4880 由 CP-SAT 证明。差距 864 来源复杂（首尾耦合 + 计算穿插），不是"还有 48 可捡"。


## 5. 适用范围与已知边界

- 本工具**只适合小用例**：划分枚举是 `E!/((E/P)!^P)`，`E=512, P=2` 时会爆炸（代码里有 `ENUM_LIMIT=200000` 会直接报错）。隐藏用例的大规模实例仍需启发式（`solver/`），CP-SAT 只能给"该实例的调度最优性"，不能给全局最优。
- 未建模内存的峰值约束（`Movl`/`Mact` 不是纯调度约束），因此候选是否可行由判题器裁决。
- 时长、依赖、引擎归属全部复用 `judge.core.model`，**不另写一套公式**——避免"两边一致但都错"。

## 7. ex3 = 6072 的独立复核（不用 CP-SAT）

CP-SAT 的 `OPTIMAL` 是机器可验的证明，但它是"黑盒结论"。为了能被人核对，另外写了一个
**不依赖 OR-Tools、也不依赖求解器**的穷举器：`tools/ex3_verify.py`。

**原理**：任何调度的不变式是"每台引擎上操作的先后次序"。给定次序，把每个操作尽量早地排
下去得到该次序下最早的调度；任何真实调度都对应某个次序，因此

```
min over 全部次序 = 真正的最优 makespan
```

这是个**松弛**——计算引擎的互斥被去掉（等价于假设计算引擎容量无限）。去掉约束只会让最小值
更小，所以松弛后的最小值仍是 6072，就说明真实最优**不可能低于** 6072；而 6072 已有一份合法解，
于是两者相等。

**规模与结果**：

| 网格 | 枚举量 | 结果 |
| --- | --- | --- |
| `P=2, V=2` | 3 175 200 种次序组合（两个卡组各 2520 种，用 microbatch 对称性剪半） | **6072** |
| `P=4, V=1` | 12 870 种（单卡组 16 个通信操作的两个 8 长链交错） | **76800** |

`P=4` 的 76800 与题面 §7.3 自己给出的对照值完全一致，这是对穷举器本身的交叉验证。

**消融**：把全部计算时长置零，同一穷举器给出 `6000 = 1000 + 4000 + 1000`——说明 6072 里的
72 就是 4 个 18 单位的计算操作落在关键结构上。

### 7.1 手算能到哪

| 段 | 下界 | 依据 |
| --- | --- | --- |
| 头 | 1018 | G1 任一通信操作都要等 `comb(层0)`：`disp 500 + gemm 18 + comb 500` |
| 中 | 4000 | G1 的 8 个通信操作（2 mb × 4）各 500，全落在同一套通信引擎上 |
| 尾 | 1018 | G1 最后一个操作必是 `disp_bwd`，其后还有 `comb_bwd 500 + gemm_dx 18 + disp_bwd 500` |

⇒ `Time ≥ 6036`（严格）。剩下的 36 是两处 18 单位的 `gemm` / `gemm_dx` 等待，需要联合分析
两个卡组的释放时刻才能证明无法填掉；穷举器给出的 6072 已经覆盖了这一步。

**注意**：不要以为"G1 内部的跨度最小值"就能补上这 36。把释放时刻全部放开（都取 0）后，
单引擎 8 个操作的最短跨度就是 **4000**，一个 18 都不多。36 完全来自**与 G0 的耦合**。
