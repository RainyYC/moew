## 一、fill_boost（填充气泡专项）— −0.25%

调度器出堆键原本是 `rt`（依赖就绪时刻）。`fill_boost` 把它改成

```
rt − bv[v][mb],   bv[v][mb] = fb · (fs−v)/fs · (fm−mb)/fm   （线性斜坡）
                  bv[v][mb] = fb                            （平坦）
```

意思是"前 `fs` 个 stage × 前 `fm` 个 microbatch 的**前向**操作按位置线性地显得更急"，
把前向波主动往前推。实际开始时间仍是 `max(依赖完成, 引擎空闲)`，所以依赖与引擎互斥
都不受影响——**只改取的顺序，不改取到之后的排法**。

两个关键点（第一版都做错了，导致第一次实验得出"无收益"的错误结论）：

1. **量级**：`fb` 是绝对时间，必须与用例的时间尺度同阶。参考实现用 `2e9~1e10`，
   对应它那种 `T·F_s ≈ 1e9` 的规模，即"2–10 个 per-batch 时间"。第一版用了
   `200~20000`，小三个数量级，等于没开。
2. **形状**：二维线性斜坡（stage × microbatch），不是一维的 `decay^layer`。

落地上用 `fb = plan.lb / nmb × ratio`，`ratio ∈ {0.5, 1, 2, 5, 10}`，自动适配任意尺度。

生效条件（门槛）：`nmb ≤ 1.2·V`（填充不满）或 `Time > 1.25·lb`（离下界远）。
否则前向波本来就铺得开，纯属浪费预算。预算上限 1.6 s。

单例最好：`x02` −3.94%、`x18` −3.38%、`x01` −3.35%、`x19` −3.11%。

反直觉的一条：**把网格收紧反而更差**（3 档 × 4 变体 × 0.9 s → 21,897,645）。
boost 的**量级覆盖**比变体覆盖重要，最优点常落在中间档。

## 二、精确放置 `exact_row` — −0.34%

LPT 会把大负载专家均匀分给所有 rank，最后各 rank 负载**完全相同**，形成"同构局部最优"，
1-1 / 2-2 交换全都破不了。

`r16_p4_trap` 每层负载 `[374×4, 258×6, 26×6]`，`T=3200, P=4`：

| | m | 相对下限 |
|---|---|---|
| 理论最优 | **800** | 1.00（可达：`{374,374,26,26}` ×2 + `{258,258,258,26}` ×2） |
| LPT + 1-1/2-2 交换 | 916 | +14.5% |

`m` 直接乘在 `gemm` / `gemm_dx` / `gemm_dw` 三个时长上，所以这是每层稳定多花 14.5%。

`place.exact_row()`：DFS，专家按负载降序，只往负载非增的 rank 放（对称性剪枝，
同构解只搜一次），带结点预算。`E=16` 时 0.08 s 从 916 找到 800。

**两个坑**：

- 缓存键必须是**有序** slots。用 `sorted(slots)` 做键，会把层 0 的最优行套到排列不同的
  层 1 上，`m` 反而变差。
- 精确搜索的预算必须**全求解共享**（1.2 s）。`best_placement` 每个 `P` 调一次，`E=24`
  时单层 ~0.1 s，20 层 × 5 个 P 能吃掉十几秒，把 7.6 s 预算吃穿——实测 `x19` 从 8.0M
  爆到 60.7M（解仍合法，只是搜索被饿死，返回一个 20×lb 的烂解）。

## 三、放置解耦 — −0.20%

`m` 同时决定"所有计算时长"和"候选的 lb 排序"。把深下降的 `m` 直接塞进
`best_placement`，配置相对顺序就变了、搜索轨迹全变——实测 5 例改善 4 例变差
（`r24_p4_block` +2.96%），净为负。

解法是把两者拆开：

```python
place.best_placement_split(case, P) -> (rows, m, m_rank)
#  m      深下降后的 m  → 建 plan，时长更短（单调改进）
#  m_rank LPT 的 m      → 只用于 Config.lb_rank 排序
```

`Config` 新增 `lb_rank`，`enumerate_configs` 的排序键改用它。于是候选遍历顺序与基线
**逐位相同**，但每个候选真正排出来的调度都享受更短的时长。

`deep_refine_row()` 是 1/2/3 路交换下降（最重 rank 的 a 个专家与另一 rank 的 a 个对换，
a=1,2,3），能把 `m` 精确打到每层下限：`x19` 的 614→536、706→616，`r16` 的 916→800。

代价是 `C(per_rank,3)²` 的组合数：`P=1` 时 `per_rank=E` 会爆炸（实测 `r24_p4_block`
因此 Time 从 51.6M 爆到 138M），所以加 `per_rank ≤ 8 且 E ≤ 64` 的门槛。

## 交叉验证：直接跑参考实现的求解器

为了确认"参考实现在 `x19` 上真的能做到 7,474,851"，写了一个薄适配层，把它的求解器接到
本项目已与官方 grader 逐例一致的判题核心上（`Input` / `op_durations` / `validate` /
`memory_usage` / `solution_text`）。

结果：`x19` 跑出 `V=20 P=6 W=12 var=(1,0,0) fs=2 fm=6 fb=2e9 dec=1`，Time = 7,474,851，
我们的判题器复核 `合法 · Time=7,474,851` —— **与它报告的数字逐位相同，可信**。

它同时暴露了 `x19` 的差距来源：它的 `lb = 2,661,120`，我们的是 `2,920,320`，差的全是
`m`（它 536/616 = 每层下限，我们 614/706）。所以 `x19` 也是放置问题，不是填充问题。

## 仍然落后的地方

相对参考实现（均值 22,789,916）：**39 胜 11 负，均值快 4.60%**，几何比值 0.9542。

仍落后的 11 例里只有两例还有意义：`x19` 1.039、`x02` 1.036；其余 9 例在 0.0%–2.1%，
属于搜索噪声级。

`x19` 剩下的 3.9% 已经不是放置（`m` 已到下限、lb 与对方一致），而是它自己的调度结构：
`L=20, nmb=12, V=20`，20 级流水线只灌 12 个 microbatch，永远填不满。

## 一个未解决的观察

解耦版有 2 例变差（`x02` +4.10%、`x05` +1.90%）。排序键逐位相同、时长只会更短，
理论上不该发生。判断是**预算边界效应**：单个调度变快后，同一时间片内会试更多候选，
反而可能错过原本命中的那个。这是搜索的时序敏感性，不是改动本身有害；要消除需要按
"已试候选数"而非墙钟分配预算，风险更大，暂未动。
