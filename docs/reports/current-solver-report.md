# 当前求解器完整解题报告

报告日期：2026-10-31。求解器使用 C++17，多个实现文件分别编译后链接；入口为 [src/solver.cpp](../../src/solver.cpp)，可选裁判单文件为 [submission/solver.cpp](../../submission/solver.cpp)。第 1–3 节建立问题模型和术语，第 4–10 节解释算法，第 11 节说明软件设计与运行方法，第 12–14 节给出验收结果和复核资料。

把一次基本计算或通信任务称为一个**操作**。本题要选择硬件分配和操作时间表，使最后一个操作尽早完成。求解器先比较如何分配硬件与模型层，再改进计算、通信操作的先后次序。后文按“要决定什么、怎样生成一个方案、怎样改进已有方案”的顺序展开。

文中的算法描述以当前模块源码为准，正式验收数据来自一次完整的官方 50 例运行，不把多次运行的最好结果拼接成一个批次。第 12 节另列历史参考的口径，用于解释标签与本次整合效果。构建与验收过程见[验收记录](../../results/optimization_integration/README.md)。

## 1. 问题与优化变量

### 1.1 输入

先明确输入所描述的几个对象。**专家**是处理一部分输入的计算单元；每个 token 会被路由到 $k$ 个专家，称为 top-$k$ 路由。一次“token 分给一个专家”的负载记为一个 **token-slot**，因此层负载 `T[l]` 已经包含这 $k$ 份分配。共享专家执行该层共有的计算，不参与可路由专家的分组。

**microbatch（微批次）**是分别推进的一小批数据。不同硬件分组可以同时处理不同微批次，形成**流水线**。每个微批次都经过模型的前向计算和反向梯度计算；下文用 $B=mb$ 表示微批次数，用 $m\in[0,B)$ 表示其中一个微批次的编号。前向产生、需要保留到反向使用的中间数据称为**激活值**，通信期间用于暂存数据的空间称为**通信缓冲**。输入给出每层的固定专家负载，同一层的各微批次按同一时长模型处理。

| 字段 | 含义 |
|---|---|
| `N, S` | 节点数、每节点卡数；总卡数 $R=NS$ |
| `M` | 每张卡的内存上限 |
| `Bi, Bo` | 节点内、节点间带宽 |
| `L, E` | 层数、每层可路由专家数 |
| `Z, Zs` | 单个可路由专家、共享专家的参数驻留量 |
| `U, Ua` | 一块通信缓冲、一个 microbatch 在一层的激活内存 |
| `k, mb` | top-k、microbatch 数；下文记 $B=mb$ |
| `Fs, Fio, Fin` | 共享专家计算、通信、路由专家计算系数 |
| `ax, bx` | 以百万分之一为单位的反向计算系数 |
| `d, b` | 隐层宽度、每元素字节数 |
| `T[l]` | 第 $l$ 层的总 token-slot 数 |
| `load[l][e]` | 第 $l$ 层专家 $e$ 的 slot 数 |

输入前三行依次为集群参数、模型参数和 `d b`，随后是 $L$ 行负载。合法负载行可以只给 `T[l]`，或追加完整的 $E$ 项专家负载。省略时，求解器以商和余数均匀展开：每个专家先分得 $\lfloor T_l/E\rfloor$，前 $T_l\bmod E$ 个专家再加一。

解析器按行读取负载；只有该行追加值恰好为 $E$ 项时才采用显式向量。因此，它假定输入满足官方格式，不承担全面的输入错误诊断。

### 1.2 四类决策

共同执行一段模型层的若干张卡构成一个**卡组**；`rank` 是卡组内部卡的编号。每个微批次在每层执行十种固定操作，具体含义列于第 2.1 节，所以整个时间表的操作总数为 $J=10LB$。

1. **并行网格 $(V,P)$**：$V$ 个卡组，每组 $P$ 张卡，满足 $VP\le R$、$P\mid E$，且 $P\mid S$ 或 $S\mid P$。
2. **切层 $\psi$**：把 $L$ 层切成 $K$ 个非空连续块，其中 $K=V$ 或 $K=2V$。
3. **专家映射 MAP**：每层把 $E$ 个专家放到 $P$ 个 rank，每个 rank 恰好持有 $E/P$ 个专家。
4. **调度 SCHEDULE**：为全部 $J$ 个操作指定非负整数开始时刻。

下文把卡组规模、块切点及每层所属卡组统称为**布局**；MAP 则单独描述每层专家如何分配到组内各卡。二者确定后，操作时长与资源归属也随之确定，仍需决定各操作何时开始。

块 $j$ 所属的卡组为：

$$
g(j)=
\begin{cases}
j,&j<V,\\
2V-1-j,&j\ge V.
\end{cases}
$$

因此，$K=V$ 时每组持有一段层；$K=2V$ 时每组持有前后镜像配对的两段层。实现中的 `G` 表示实际卡组数，输出为 `V`；`K` 始终表示块数，二者不能混用。

每张物理卡按 $q=vP+p$ 对应网格坐标 $(v,p)$。同一卡组共享代表卡时间表，不另行搜索组内每张卡的调度。

### 1.3 目标

对操作 $o$，`start(o)` 是开始时刻，`duration(o)` 是按题目公式算出的持续时长，`end(o)=start(o)+duration(o)` 是结束时刻。整个时间表的完成时间定义为：

$$
\operatorname{Time}=\max_o\{\operatorname{start}(o)+\operatorname{duration}(o)\}.
$$

`Time` 越小越好，单位是题目定义的抽象时间单位，衡量所输出方案的质量。另有两项描述求解程序自身的开销：**墙钟时间**是运行实际经过的秒数，**CPU 时间**是执行求解进程所消耗的处理器时间。官方批量脚本用单例墙钟限时判断是否超时；这两个秒数都不是答案的 Time。

### 1.4 候选、当前解与搜索

**候选**是一次准备评估的布局、专家映射或时间表；**可行时间表**是满足操作依赖、引擎互斥和内存约束的完整时间表，这些约束将在第 2–3 节说明。搜索已经保留的最好完整方案称为**当前最佳解**，代码中常写作 `best` 或 `incumbent`。

**调度器**在给定布局、专家映射和调度规则后，构造一张时间表；**搜索阶段**则反复改变配置、调用调度器，并比较产生的候选。因此，“调用一次调度器”和“完成一个搜索阶段”不是同一层次的工作。第 4 节会把各搜索阶段串成完整流程。

后文还会用**下界**判断改善空间：对于某个要最小化的量，下界是在指定条件下任何可行方案都不能低于的数值。下界取决于哪些条件已固定，例如固定 MAP 的下界不能直接证明其他 MAP 也无改进空间。根据可行性条件或下界比较提前排除候选，称为**剪枝**；因运行预算不足而停止搜索，仅表示尚未继续探索。

## 2. 精确时长与依赖模型

### 2.1 每层三个基本时长

设 $a_{l,e}=\mathtt{load}[l][e]$ 为层 $l$ 的专家 $e$ 的 slot 数，$\sigma_{l,e}$ 为该专家所在的 rank。定义：

$$
\begin{aligned}
H&=\left\lfloor db/k\right\rfloor,\\
m_l&=\max_{0\le r<P}\sum_{\sigma_{l,e}=r}a_{l,e},\\
X_l&=\left\lceil T_lH/P\right\rceil,\\
p_{\rm in}&=\min(P,S)-1,\qquad p_{\rm out}=P-1-p_{\rm in},\\
c_l&=\max\left(
\left\lceil p_{\rm in}X_l/B_i\right\rceil,
\left\lceil p_{\rm out}X_l/B_o\right\rceil
\right)F_{\rm io},\\
g_l&=m_lF_{\rm in},\qquad s_l=T_lF_s.
\end{aligned}
$$

$H$ 是每个 slot 的通信载荷，$m_l$ 是该层最忙 rank 的负载，$X_l$ 是用于通信估时的每卡载荷；$p_{\rm in}$、$p_{\rm out}$ 分别计入节点内、节点间对端。三个基本时长 $s_l$、$g_l$、$c_l$ 分别对应共享专家前向、路由专家前向和一次前向通信。

专家映射直接改变 $m_l$，进而改变路由专家计算时长。增大 $P$ 可以降低每卡专家驻留和计算负载，也可能增加通信代价，并减少可用卡组数 $V$。这些作用需要通过实际调度比较。

定义整数缩放函数：

$$
A(x)=\left\lceil \mathtt{ax}\cdot x/10^6\right\rceil,\qquad
D(x)=\left\lceil \mathtt{ax}\cdot\mathtt{bx}\cdot x/10^{12}\right\rceil.
$$

这里 `ax`、`bx` 是输入字段名，乘法和向上取整按整数执行。

每个卡组有计算、通信两类**引擎**，分别表示能够独立占用的计算资源和通信资源。前向将输入变成输出；反向一部分计算输入梯度，用于继续向前一层传递，另一部分计算权重梯度，用于更新本层参数。十种操作如下：

| 编号 | 操作 | 含义 | 引擎 | 时长 |
|---:|---|---|---|---:|
| 0 | `s` | 共享专家前向 | 计算 | $s_l$ |
| 1 | `disp` | 将前向数据分发给专家 | 通信 | $c_l$ |
| 2 | `gemm` | 路由专家前向计算 | 计算 | $g_l$ |
| 3 | `comb` | 汇集专家前向结果 | 通信 | $c_l$ |
| 4 | `s_bwd` | 共享专家输入梯度 | 计算 | $A(s_l)$ |
| 5 | `comb_bwd` | 汇集操作的反向通信 | 通信 | $A(c_l)$ |
| 6 | `gemm_dx` | 路由专家输入梯度 | 计算 | $A(g_l)$ |
| 7 | `gemm_dw` | 路由专家权重梯度 | 计算 | $D(g_l)$ |
| 8 | `disp_bwd` | 分发操作的反向通信 | 通信 | $A(c_l)$ |
| 9 | `s_dw` | 共享专家权重梯度 | 计算 | $D(s_l)$ |

### 2.2 操作 DAG

把操作视为节点，把“前一个操作必须完成，后一个才能开始”视为有向边，就得到操作依赖图。图中不存在依赖环，称为 **DAG（有向无环图）**；一条边的起点是终点的前驱。按前驱在前、后继在后的顺序访问节点，称为**拓扑顺序**。每个 microbatch、每层的局部依赖如下：

~~~mermaid

    s["s"] --> comb["comb"]
    disp["disp"] --> gemm["gemm"] --> comb
    comb --> sb["s_bwd"]
    comb --> cb["comb_bwd"]
    cb --> dx["gemm_dx"]
    cb --> dw["gemm_dw"]
    cb --> sw["s_dw"]
    dx --> db["disp_bwd"]
    sb --> db
    classDef fwdCompute fill:#eff6ff,stroke:#2563eb,color:#1e3a8a
    classDef fwdNetwork fill:#ecfeff,stroke:#0891b2,color:#155e75
    classDef bwdCompute fill:#fff7ed,stroke:#ea580c,color:#9a3412
    classDef bwdNetwork fill:#faf5ff,stroke:#9333ea,color:#6b21a8
    class s,gemm fwdCompute
    class disp,comb fwdNetwork
    class sb,dx,dw,sw bwdCompute
    class cb,db bwdNetwork
~~~

相邻层还存在两组边：

- 前向：第 $l-1$ 层的 `comb` 完成后，第 $l$ 层的 `s`、`disp` 才能开始。
- 反向：第 $l+1$ 层的 `disp_bwd` 完成后，第 $l$ 层的 `s_bwd`、`comb_bwd` 才能开始。

两个权重梯度操作 `gemm_dw`、`s_dw` 只依赖本层 `comb_bwd`，没有阻塞相邻层反向传播的后继边。调度器据此把它们移到空闲时段，优先推进决定流水线进度的操作。

每个卡组有独立的计算、通信引擎；同一引擎上的正时长操作不能重叠，两类引擎之间可以重叠。操作不可拆分或抢占。不同 microbatch 之间没有模型 DAG 边，但会竞争相同的引擎并共同消耗内存。

### 2.3 调度模式：怎样从可选操作中做选择

依赖和资源约束通常不能唯一确定时间表：同一引擎可能同时有多个操作可选。**调度模式**在本文中指生成时间表时采用的选点、排序或放置规则。它影响先选择哪个操作，所有选择仍必须满足同一组合法性约束。

**就绪集合**保存当前可以交给调度规则选择的操作。事件调度要求其前驱已经完成；列表调度要求前驱已经排定、结束时刻已知，再把待选操作安排到这些时刻之后。就绪不等于立即占用引擎，实际执行还需要满足资源与内存条件。当前工程有两种调度内核：

| 调度内核 | 构造时间表的方式 | 多个操作可选时怎么办 |
|---|---|---|
| 事件调度 | 维护一个模拟时刻，启动当前能运行的操作，再推进到下一事件 | 在每个引擎的就绪队列中按优先级选点 |
| 离线列表调度 | 依次选择操作，为它计算依赖和资源允许的放置时刻 | 按预设次序或最早可执行时间排序 |

事件调度使用的**剩余路径时长**，是只沿模型 DAG 从该操作走到后继终点的最大时长和，包含该操作自身，不包含其他微批次造成的资源等待。

第 5 节会用到以下三个事件优先级模式，编号是内核配置值：

| 内核模式 | 主要选择规则 | 目的 |
|---|---|---|
| `mode=0` | 按固定操作类别排序：输入梯度相关操作优先，随后推进已有前向，权重梯度靠后 | 尽快推进反向依赖，并让已进入流水线的工作继续前进 |
| `mode=1` | 先区分输入梯度、前向和权重梯度三类；同类中优先剩余路径较长者 | 在保持反向偏好的同时照顾后续工作较多的分支 |
| `mode=2` | 按类别和剩余路径建立队列，再查看每个引擎队首最多 16 个候选；跳过当前受阻者，偏好能补齐依赖汇合、帮助回收激活的操作 | 利用局部状态减少等待，不局限于只看队首一个节点 |

例如，某层的 `gemm` 已完成而 `s` 尚未执行时，完成 `s` 就可能使 `comb` 获得全部前驱结果；模式 2 会考虑这种“补齐汇合”的价值。该优先级仍只作用于已满足自身依赖的候选。

后文把两种内核称为“事件调度器”和“列表调度器”，把上表称为“事件优先级模式”。命令行的 **搜索模式 `--mode`** 则决定启用哪些搜索阶段，其范围在第 4 节说明；它与内核的数值 `mode` 不共用编号。第 11 节的“策略设计模式”讨论代码如何组织这些内核，也属于另一个层次。

### 2.4 窗口、波前与局部重排

允许一个微批次进入调度候选集合称为**准入**，它不代表这个微批次的全部操作立即执行。**窗口 $W$** 控制准入节奏：事件调度器限制同时占用窗口名额的微批次数；列表调度器让相隔 $W$ 个编号的微批次之间满足入口等待条件。名额何时归还，分别在第 6.2、7.1 节定义。**全窗口**表示 $W=B$，不再用较小窗口限制入口；事件接口另允许用 0 表示不额外限制窗口。两者都保留依赖与内存约束。

**空档**是某一引擎时间表上尚未被操作占用的时段；**填空**是在满足依赖的前提下，把操作放进已有空档。**波前**则是一类列表排序规则：结合微批次编号与前后向推进位置，让不同微批次交错前进。位置可以用层号衡量，也可以用依赖图推算的时间衡量。波前在本工程中由列表内核执行，不另设第三套调度内核。

**局部重排**保留布局和专家映射，只尝试改变同一引擎上部分操作的先后次序，再重新推算开始时刻；后一步称为**重定时**。一次允许修改能产生的备选顺序集合称为**邻域**。把模型依赖与当前引擎先后关系放入同一约束图后，决定最早完成时间的最长路径称为**关键路径**；第 9 节围绕它构造重排邻域。

这段搜索先尝试在小例上执行少量有明确轮数上限的调用，称为**搜索前缀**；再利用剩余时间追加调用，称为**扩展阶段**。两者的具体评估额度见第 9.3 节。

## 3. 内存约束与端点语义

设卡组 $g$ 持有 $n_g$ 层，每层每卡的参数驻留量为：

$$
q=(E/P)Z+Z_s.
$$

官方内存条件为：

$$
n_gq+U\cdot C_g^{\max}+U_a\cdot A_g^{\max}\le M.
$$

其中：

- $C_g^{\max}$：本组所有**正时长通信操作**区间 $[start,end]$ 的最大重叠数。
- $A_g^{\max}$：本组所有激活区间 $[end(comb),start(s\_bwd)]$ 的最大重叠数。
- 两类峰值分别计算后相加，即使二者出现在不同时间，也不能改为扫描瞬时总内存后只取一次峰值。
- 激活区间即使长度为零仍计入；零时长通信不计通信缓冲。

引擎冲突允许操作在同一时刻首尾相接，内存则使用闭区间。例如通信区间 $[0,5]$ 与 $[5,9]$ 在时刻 5 要同时计两块缓冲；改为 $[0,5]$ 与 $[6,10]$ 才只需一块。因此，通信之间是否留一个时间单位，会同时影响 Time 和激活可用空间。

实现既可以预留空间，也可以在构造时间表后核对区间峰值。预留一个**激活槽**，就是先占用一份 $U_a$ 字节的激活额度，不要求对应激活已经实际产生。具体路径如下：

| 路径 | 方法 |
|---|---|
| 事件调度 | 先从参数驻留与通信缓冲预算算出激活容量；microbatch 准入时保守预留各层激活槽 |
| 列表、波前、普通局部候选 | 生成候选后按实际通信和激活区间扫描峰值，超过上限则拒绝 |
| 局部搜索快路径 | 仅当逐组保守上界不超过 $M$ 时跳过逐候选峰值扫描；其他组使用上方完整扫描 |

区间扫描只在 `end < next_start` 时移除结束事件，保留同刻端点的重叠，符合官方 grader 的口径。

## 4. 总体流水线

### 4.1 搜索模式决定哪些阶段参与

搜索模式是运行整个求解器时选择的阶段组合，由命令行 `--mode` 指定。它决定搜索范围；进入某个阶段后，仍由该阶段选用第 2.3 节的调度内核和优先级规则。各阶段的运行预算从解析参数前记录的同一起点累计，具体截止位置见第 10.2 节。

| 搜索模式 | 执行范围 | 适用目的 |
|---|---|---|
| `full`（默认） | 初始布局与专家映射、事件类精化、列表搜索、波前，以及满足条件的资源下界布局搜索、优先级重建和局部重排 | 正常求解与官方验收 |
| `list` | 完成初始与事件类搜索，再执行列表搜索；在额外布局、波前和局部重排之前结束 | 观察列表阶段能得到的结果 |
| `event` | 完成初始布局、事件类精化、窗口与专家组合搜索，不执行列表及后续扩展 | 单独观察事件类搜索效果 |
| `serial` | 选择初始可行布局后，按合法前后向次序串行输出操作，并在相邻操作之间留一个时间单位 | 检查输入、布局和输出链路 |

`full` 中各阶段仍受规模条件和剩余时间限制，并非每例都会执行每个分支。`list` 搜索内部可以调用一次采用波前规则的快速填空；这里关闭的是后续专门的波前搜索阶段，不能把模式名理解成禁止内核使用某类排序规则。

### 4.2 默认模式的方案传递

初始筛选先构造计算便宜的近似负载，称为**代理值**，再用**动态规划（DP）**比较连续切层方案。代理值用于缩小候选集合，实际 Time 仍由构造出的时间表决定。**探测**是一次较便宜的真实调度评估；**精化**是在选出的配置附近再测试更多规则。

阶段之间传递完整解：并行规模、块切点、层到组映射、专家映射、开始时刻以及 Time。作为后续搜索起点保留的方案称为**种子**，一个种子可以暂时差于全局当前最佳解；分支搜索完成后，仍按完整方案的 Time 决定是否更新全局答案。常规候选只在 Time 严格下降时替换当前解；局部资源重排还允许 Time 相等、全部操作结束时刻之和下降的移动。

## 5. 初始专家映射与层布局

### 5.1 定容量负载均衡

对每层、每个候选 $P$：

1. 把专家按负载从大到小排序。
2. 依次分配给尚未达到 $E/P$ 个专家、且当前总负载最小的 rank。
3. 最多进行 6 轮两专家交换：枚举来自不同 rank 的专家对，比较交换后的最大 rank 负载；最大值相同时，比较各 rank 负载平方和。
4. 如果已达到下界
   $$
   \max\left(\max_e a_{l,e},\left\lceil\sum_ea_{l,e}/P\right\rceil\right),
   $$
   或不存在改进交换，则停止。

交换不改变每个 rank 的专家数量。平方和作为次级目标，可以在最大值暂时不变时改善其余 rank 的均衡程度。该方法提供便宜的初始映射，没有承诺获得全局最优的定容量分组。

### 5.2 连续切层 DP

合法 $P$ 满足：

$$
1\le P\le \min(R,E),\quad E\bmod P=0,\quad
(S\bmod P=0\ \lor\ P\bmod S=0).
$$

对固定 $P$，枚举 $V=1,\ldots,V_{\max}$，其中：

$$
V_{\max}=\min(L,64,\lfloor R/P\rfloor).
$$

DP 使用理想均分计算代理 $\hat g_l=\lceil T_l/P\rceil F_{\rm in}$，并定义层权重：

$$
w_l=4c_l+2\hat g_l+2s_l+
2A(c_l)+A(\hat g_l)+D(\hat g_l)+A(s_l)+D(s_l).
$$

这个权重有意对前向计算和通信加权，且采用理想均分的专家负载；它并非十种真实时长之和，也不是最终 Time。

记 $W_i=\sum_{l<i}w_l$。将前 $i$ 层切成 $j$ 段的状态为：

$$
DP[j][i]=\min_{h<i}\max\{DP[j-1][h],W_i-W_h\}.
$$

令 $z_P=\mathbf{1}_{\exists\,l\in[0,L):c_l>0}$，即检查整个模型是否存在非零通信。转移只允许非空段，并检查：

$$
(i-h)(q+U_a)+z_PU\le M.
$$

它为每层预留一份激活；只要整个模型存在非零通信，就为每个段预留一块通信缓冲，包括本身通信全零的段。这是初始保守过滤；实际并发激活与通信端点峰值仍交给调度阶段处理。

候选评分为：

$$
score=10^6 DP[V][L]+\sum_l m_l.
$$

对同一个 $P$，最后一项不随 $V$ 改变。每个 $P$ 保留两个布局代表：

- `best_v`：代理评分最小的可行 $V$ 及其切点。
- `max_v`：最大的可行 $V$ 及其切点。

### 5.3 实际调度探测与加深

先对每个 $P$ 的 `max_v` 做一次低成本事件调度：使用第 2.3 节定义的事件优先级模式 0，不额外限制窗口，并为有通信的卡组使用一块通信缓冲。随后按实际探测 Time 排序。

**加深评估针对前两名 $P$**。每个入选 $P$ 使用其 `best_v`，探索不同窗口、优先级以及通信缓冲数。初选第一名还探索镜像布局和切点移动。

普通布局的精化组合包括：

- 窗口：去重后的 $\{0,1,2,G,2G\}$，其中 0 表示不额外限制。
- 事件优先级模式：0、1、2。
- 通信缓冲：一块，以及内存允许时的两块；全零通信组为零块。

镜像布局使用 $K=2G$ 个近似等长的非空块，按镜像规则归组。候选 $G$ 来自最大可用镜像组数、当前 $V$ 和约一半 $V$ 的有限集合。

切点精化按边界两侧层总时长差排序，最多挑选三个边界，分别尝试向左或向右移动一层。每次从固定种子切点出发，并保证所有块非空，因此不构成切点组合的穷举。

## 6. 事件调度与专家组合搜索

### 6.1 事件调度器

调度器为 $J$ 个操作建立 DAG，每个 `(group, engine)`（卡组与引擎的组合）维护就绪队列，另用事件堆保存操作完成和激活归还事件。通信还可能需要等待上一次通信的缓冲区端点不再冲突，称为通信冷却；它的计算规则见第 6.2 节。

时间推进步骤为：

1. 处理当前时刻的全部完成、归还事件。
2. 根据前驱计数解锁新节点，并尝试准入 microbatch。
3. 扫描各组两类引擎，按优先级启动可运行操作。
4. 零时长操作立即完成并解锁后继；必要时重扫同一时间点，直到不能继续推进。
5. 跳到下一个完成或通信冷却时刻。

第 2.3 节的事件优先级模式 0、1、2 具体作用于步骤 3：分别按固定类别、类别与剩余路径、有限队首候选检查选择操作。改变这个规则会生成不同时间表，但不改变步骤 1–5 的事件推进框架。

### 6.2 激活槽、窗口和通信冷却

事件调度器把可用于激活的空间换算为**激活槽**：一个槽代表一份微批次在一层的激活所需的 $U_a$ 字节。设为卡组 $g$ 预留的通信缓冲数为 $buf_g$，它的激活槽容量为：

$$
cap_g=\min\left(
\left\lfloor\frac{M-n_gq-buf_gU}{U_a}\right\rfloor,\ Bn_g
\right).
$$

准入一个 microbatch 时，为它在每组预留 $n_g$ 个槽。每个 `s_bwd` 在开始后的一个时间单位归还对应槽，覆盖激活闭区间的结束端点。

窗口 $W$ 还限制同时准入的 microbatch 数，默认在整个 microbatch 的全部操作完成后释放窗口名额。补充搜索另试一种较早释放方式：第 0 组在该 microbatch 的全部 `s_bwd` 完成后，便释放全局窗口名额。窗口名额和激活槽是两个独立约束，不能把“释放窗口”解释成一次性释放全部激活内存。

通信引擎在一块缓冲时至少等待到上一段通信结束后一个时间单位；两块缓冲时允许首尾相接，同时通过开始时间约束避免闭区间端点叠出更多缓冲。

### 6.3 窗口扫描

窗口扫描分别围绕最佳探测解和初始精化解进行。若 $B\le64$，枚举 $W=1,\ldots,B$；否则使用固定值与 $G$、$2G$ 附近的稀疏候选，包括不额外限制的窗口。

这里保持布局和专家映射不变，只改变通信缓冲、激活容量及准入节奏。较小窗口有利于控制激活和反向延迟；较大窗口有利于填满流水线，最终仍由实际 Time 决定。

### 6.4 利用少量负载类型优化专家分组

若某层初始映射的最大 rank 负载高于理论下界，尝试按相同负载值压缩专家集合。当前组合搜索支持：

- 至多 4 种不同专家负载；
- $P\le32$；
- 每 rank 专家数 $E/P\le32$。

给定目标峰值 $C$，先枚举一个 rank 可以容纳的“各负载类型数量向量”，称为**配额组合**，例如每种负载分别放几个专家。随后用深度优先搜索（DFS）逐个 rank 选择配额组合，检查剩余专家数量、容量及类型计数。搜索用组合访问次序消除等价 rank 之间的重复枚举，并记忆失败状态，避免重复搜索。

目标峰值在理论下界到当前最大负载减一之间二分，最多 12 次可行性查询；每次查询的共享搜索访问预算为 250,000。相同排序负载向量的成功方案可以跨层缓存，随后映射回原专家编号。

预算耗尽也会返回失败，因此“未找到”不等价于数学不可行，二分结果也不构成最优性证明。只有重新聚合实际 rank 负载后确认峰值下降，才采用新 MAP；之后重新计算时长和调度，再与全局当前解比较。

## 7. 离线列表调度

事件调度在当前时刻立即选择任务。离线列表调度则按某种拓扑优先级逐个放置操作，计算前驱、窗口及资源允许的最早时间；启用填空时，还能把后来处理的操作插入已构造时间表的空档。

### 7.1 排序与窗口

普通列表候选使用 8 个预设排序变体。一个变体定义操作类别、microbatch 编号和层号的比较次序；实际选择仍只在满足依赖的候选中进行。编号对应列表内核的 `variant` 字段，不是事件优先级模式 0/1/2 的延续编号。

| 变体编号 | 优先的方向 | microbatch 编号次序 | 层号次序 | 同方向内先比较 |
|---:|---|---|---|---|
| 0 | 前向 | 从小到大 | 从小到大 | microbatch 编号 |
| 1 | 前向 | 从小到大 | 从大到小 | microbatch 编号 |
| 2 | 前向 | 从大到小 | 从小到大 | microbatch 编号 |
| 3 | 前向 | 从大到小 | 从大到小 | microbatch 编号 |
| 4 | 反向 | 从小到大 | 从小到大 | microbatch 编号 |
| 5 | 反向 | 从大到小 | 从大到小 | microbatch 编号 |
| 6 | 前向 | 从小到大 | 从小到大 | 层号 |
| 7 | 反向 | 从大到小 | 从小到大 | 层号 |

例如，变体 1 在同为前向的就绪操作中先比较微批次编号，编号相同时偏好更深的层；变体 6 先比较层号，再比较微批次编号。第 8 节的波前候选会换用专门的波前排序键。

两种选点方式分别为：

- `priority`：主要按预设优先级排序。
- `early`：入队时把可放置时间纳入队列键；取出时重新计算时间键，必要时重新入队。最终放置仍检查资源与窗口，前向奖励对时间键的调整见第 7.3 节。

列表窗口的实际门控发生在第 0 层的无前驱入口 `s`、`disp`。设 $g_0=group[0]$，当 $m\ge W$ 时：

$$
start(m,0,\text{入口})\ge
\max_{l:group[l]=g_0}end(m-W,l,s\_bwd).
$$

代码虽然为全部卡组维护释放计数，但入口门控只读取第 0 层所属组。该规则不要求等待前一窗口中的全部权重梯度结束。

### 7.2 空档填充

每个卡组、每类引擎维护可用空档。对待放置的正时长操作，寻找满足全部依赖且长度足够的最早空档；放置后拆分或移除该空档。没有合适空档时，追加到引擎尾部。

填空只在通信间隔参数为 0 时启用。通信间隔为 1 的候选通过增加时间换取较低通信缓冲峰值，之后仍须完整内存检查。

为判断当前时间表还有多少空间，先定义**固定布局的资源负载下界**。记 $C_l$、$N_l$ 分别为单个微批次在层 $l$ 上所有计算操作、所有通信操作的时长之和。同一卡组的同一引擎必须串行承担全部 $B$ 个微批次的工作，所以任何时间表的 Time 都不可能低于最忙引擎的总工作量：

$$
LB_{\rm fixed}=B\max_g\left(
\sum_{l:group[l]=g}C_l,\
\sum_{l:group[l]=g}N_l
\right),
$$

节点数在 5,000 至 150,000、累计运行尚不足 4 秒时，离线阶段先尝试一次全窗口波前填空。若填空已经改善当前解，且 Time 不超过上述下界的 1.08 倍，代码可跳过宽泛窗口扫描，将剩余预算留给其他搜索。

### 7.3 优先级扫描与前向奖励

后续搜索试验不同窗口、排序方式及通信间隔 0/1，优先覆盖部分排序和窗口，再按剩余预算补充其他组合。

部分 `early` 候选还给早期卡组、早期 microbatch 的前向操作加入排序奖励。奖励量由固定布局的瓶颈引擎工作量、比例和作用范围决定，可以均匀施加或逐步衰减。它只改变选点顺序，不改变真实操作时长。

所有被考虑保留的列表候选均检查操作完整性和实际闭区间内存；DAG 和引擎互斥由放置过程保证。没有通过内存检查的候选不会进入最终解。

## 8. 扩展布局与波前搜索

### 8.1 额外 P 候选

满足下列条件时，算法探索与当前解不同的至多两个 $P$：

- 默认扩展搜索已启用；
- $B\le16$，且 $10LB\le8000$；
- $L>G$；
- 尚未到本例波前阶段的绝对截止点，并能为下一次布局评估保留约一秒预算；小规模完整搜索使用第 10.2 节的较早截止点。

候选按初始探测 Time 排序。对候选映射，定义：

$$
G_{\max}=\min(L,64,\lfloor R/P\rfloor),
$$

$$
LB=\max\left(
B\max_l C_l,\
B\max_l N_l,\
\left\lceil B\sum_l C_l/G_{\max}\right\rceil,\
\left\lceil B\sum_l N_l/G_{\max}\right\rceil
\right).
$$

若这个下界已经不小于当前 Time，则跳过该候选。该下界基于当前候选 MAP 的操作时长，用于剪去本次布局评估；它不证明采用其他专家映射的同一个 $P$ 也无法改善。

通过筛选的候选执行普通布局、镜像布局和切点精化。即使其事件调度未超过当前解，也保留为后续波前搜索的种子。

### 8.2 九种初始波前

这里把第 2.4 节的波前概念具体化：为每个操作构造一个排序键，比较微批次编号 $m$ 与操作在前后向中的推进位置。只考虑模型 DAG、暂时忽略引擎争用时，可推算操作的**最早开始时刻 ES**；加上自身时长得到**最早完成时刻 EFT**。这两个量用于排序，实际开始时刻仍由列表调度器结合资源和窗口计算。

波前搜索以离线阶段最佳解和额外布局种子为起点，对每个种子先测试 9 个全窗口候选：

| 类型 | 排序思想 | 数量 |
|---|---|---:|
| 加权对角波前 | $2m+(l\text{ 或 }2L-l)$，前向使用 $l$，反向使用 $2L-l$ | 1 |
| 时长波前 | DAG 最早开始 ES 或最早完成 EFT，搭配 $1/4,1/2,1$ 三档 microbatch 间距 | 6 |
| 权重梯度次序 | EFT、$1/2$ 间距，分别偏好短或长权重梯度 | 2 |

时长波前取 $h(o)$ 为操作 $o$ 的 ES 或 EFT，取 $p_n/p_d$ 为微批次间距比例，构造整数排序键：

$$
m\cdot work_{\max}\cdot p_n+h(o)\cdot p_d,
\qquad
work_{\max}=\max_l\max(C_l,N_l).
$$

这里的 `work_max` 是最大**单层**引擎工作量。它给微批次之间的排序间距提供量纲；第 7.2 节的固定布局下界则累计每个卡组拥有的全部层，两者用途不同。

排序键首先把权重梯度放入较后的类别，再按上述波前键和次级键排序。实际可执行性仍由 DAG 和资源放置决定，排序本身不会越过依赖。

### 8.3 波前窗口精化

对每个种子，保留合法全窗口候选中 Time 最小的两个，再测试去重窗口：

$$
\{G,2G,\max(1,\lfloor B/2\rfloor),B\}.
$$

全窗口 $B$ 已测试，不重复计算。候选通过空档填充构造，并检查实际内存峰值。每个种子完成后，恢复全局当前解并只接受严格改善，避免较差种子覆盖已有结果。

波前阶段本身没有只限小规模的条件；额外 $P$ 搜索、下面的两项扩展以及局部搜索前缀有各自的规模门槛，按时间运行的局部扩展没有 $J$ 门槛。

### 8.4 固定 MAP 下的资源头尾下界

前面的初始切层 DP 主要平衡各段的代理工作量。进一步切层还需考虑流水线的启动和收尾：同样的总计算量，放在很晚才能开始、或者结束后仍有很长反向链的位置，可能拉长最终 Time。

对一个操作 $o$，定义**头部下界** $r_o$ 为它最早可能开始的时刻下界，**尾部下界** $q_o$ 为它完成之后，依赖链仍至少需要的时间。二者均不包含操作自身时长。先在单微批次 DAG 上正向、反向传播，再利用同一层、同一引擎的必经祖先或后继工作量加强下界。这里没有把当前布局的跨层资源顺序固化进去，因此可用来比较不同切层；操作时长则始终属于当前 $P$ 的同一份代表 MAP。

选择引擎 $e$、头部门槛 $R_0$ 与尾部门槛 $Q_0$，只收集满足 $r_o\ge R_0$、$q_o\ge Q_0$ 的正时长操作。对一组层集合 $A$，这些操作的单微批次工作量为：

$$
W(A,e,R_0,Q_0)=\sum_{l\in A}\sum_{\substack{o\in l,\ \operatorname{engine}(o)=e\\r_o\ge R_0,\ q_o\ge Q_0}}d_o.
$$

这些操作都不能早于 $R_0$ 开始，且各自完成后都还需至少 $Q_0$ 时间。同组同引擎必须串行处理所有 $B$ 个微批次，故当 $W>0$ 时：

$$
\operatorname{Time}\ge R_0+B\,W(A,e,R_0,Q_0)+Q_0.
$$

取两种引擎与所选门槛组合的最大值，得到组成本 $C(A)$。必须排除 $W=0$ 的组合，否则会把没有操作的门槛错误地当成约束。实现为每组门槛预先建立逐层工作量前缀和，连续段或两段并集都可快速查询。

在线程序从正时长操作的头部、尾部值中分别取至多 7 个分位点，并加入 0，而非穷举所有门槛。有限门槛得到的下界仍有效，但可能更松。各 $P$ 的 MAP、时长和下界模型保持一致；这不是允许任意 MAP 改变后的全局最优性证明。内存方面先用参数驻留量作必要条件剪枝，动态通信与激活峰值仍需对完整时间表检查。

### 8.5 连续与折返布局 DP

**连续布局**指 $K=G$，每组只持有一段。令 $D(g,j)$ 表示前 $j$ 层分成 $g$ 组时的最小最大组成本，则：

$$
D(g,j)=\min_{g-1\le i<j}\max\{D(g-1,i),C([i,j))\},\qquad D(0,0)=0.
$$

**折返布局**指 $K=2G$，外侧两段同属一组，向内逐组配对。令 $F(g,i,j)$ 表示区间 $[i,j)$ 分给 $g$ 个折返卡组的最小最大组成本：

$$
F(g,i,j)=\min_{\substack{i<a<b<j\\b-a\ge2(g-1)}}
\max\{C([i,a)\cup[b,j)),F(g-1,a,b)\},\quad g\ge2.
$$

当 $g=1$ 时，要求 $j-i\ge2$，成本为 $C([i,j))$，再选一个非空中间切点把该组拆成两块。每个完成的组数状态都可回溯出完整切分。到达阶段截止时，保留已经完成的结果；没有完成的 DP 层不会输出残缺方案。

两段并集成本由严格递增四元组 $(i,a,b,j)$ 唯一确定。缓存只分配 $\binom{L+1}{4}$ 项，采用组合编号：

$$
\operatorname{index}(i,a,b,j)=\binom{j}{4}+\binom{b}{3}+\binom{a}{2}+i.
$$

例如 $L=64$ 时为 677,040 项，128 位成本约 10.8 MB，另有是否已计算的标记。缓存超过实现上限时跳过折返 DP，仍保留连续 DP 和邻域候选。这是内存保护，不是对剩余布局作不可行判定。

### 8.6 镜像切点、层数重分配与插值

DP 给出的最小下界布局未必产生最小实际 Time，因此还保留已有布局附近的候选。实现使用 `ScheduleResult.G/K/cuts` 作为当前实际布局；候选对象中的初始切分不能代替最终输出切分。

- **镜像成对移动**：在折返布局中同时把切点 $j$ 与 $K-j$ 移动相同的整数距离。前半段增加的层数由同组后半段抵消，因而保持各组总层数 $n_g$；改变的是层的位置与前后向交汇关系。还尝试少量多对组合。
- **层数重分配**：移动少量选定的单个切点，通常改变相邻卡组的总层数，在工作量均衡和流水线头尾之间换取更好的折中。折返布局中央切点 $j=G$ 是例外：它只调整同一卡组前后两块的分界，不改变该组总层数。
- **已有布局与 DP 布局插值**：仅当 $P,G,K$ 相同、使用同一份 MAP 时，按 $\psi_j(t)=\operatorname{round}((1-t)\psi_j^{\mathrm{seed}}+t\psi_j^{\mathrm{DP}})$ 生成中间布局。使用少量 $t/16$ 比例，再前后修正切点，保证块非空、首尾覆盖所有层。

相同切分去重后，按资源下界为每个 $P$ 留至多 12 个布局，并轮流调用事件和列表调度器评估。下界用于排序，不等于实际分数；只有得到完整合法时间表后才可能更新答案。阶段保留至多 8 个不同布局种子交给下一阶段，即使某个种子暂时差于全局最佳，也可能在更合适的操作排序下改善。

### 8.7 扩展排序与非均匀微批次间距

这一阶段固定某个种子的布局和 MAP，从模型 DAG 重新构造时间表，而非只交换原时间表中相邻操作。全局最佳布局先进入候选队列，再对去重后的多布局种子分配剩余预算。

首先扫描更广的排序参数：波前微批次权重、层推进权重、反向相位、权重梯度次序与窗口。时长波前先测试 6 组确定性的全窗口配置，再用由输入和布局生成的确定性随机种子抽取其他组合。所有用例使用同一套生成规则，不读取用例名称、预存答案或用例到参数的查找表。

**随机优先级**为每个 DAG 节点生成可复现的扰动键，与微批次和层推进位置组成排序键。它只影响已经满足依赖条件的候选之间的次序；资源空档、窗口与最终可行性检查照常执行。扰动强度和推进权重不同，可以使搜索离开已有资源顺序的局部邻域。

**非均匀微批次间距**则把第 8.2 节均匀的 $m\cdot work_{\max}$ 项改为可变偏移。维护整数向量 $a_0=0\le a_1\le\cdots\le a_{B-1}$，分母 $D=64$；均匀初值为 $a_m=64m$。排序键改为：

$$
\left\lfloor\frac{a_m\,work_{\max}\,p_n}{64}\right\rfloor
+h(o)p_d+\mathbf{1}_{\mathrm{backward}}\,\phi\,work_{\max}p_n.
$$

这里的 $a_m$ 是**排序偏移，不是强制开始时刻**；$\phi$ 是反向操作的排序相位。改变它们只改变列表调度器的选择顺序，真实开始时刻仍由依赖、引擎和空档决定。

在表现最好的时长波前配置上，先测试 $\phi\in\{-2,-1,0,1,2\}$，再按 $\pm1,\pm4,\pm16,\pm64$ 修改单个偏移或其后全部偏移。修改单项会改变两侧间距；修改后缀相当于调整一处微批次间隙。最后尝试少量多点组合，所有向量必须保持非负、单调。每个布局的参数扫描最多使用约 3/5 预算，给偏移搜索保留约 2/5；两个子阶段仍受统一绝对截止点约束。

### 8.8 候选验证与晋级

资源下界布局与优先级重建这两个新增阶段的输出，都经公共验证器 `is_feasible_schedule` 检查；基础波前阶段保留自己的闭区间校验路径。内核产生的操作顺序可能不是开始时间顺序，尤其空档填充会把后来选中的操作放到更早空档，因此新阶段先按开始时刻和操作标识稳定排序，再验证。

验证内容包括：合法网格、每 rank 专家数、非空完整切分及组映射、每个操作恰好出现一次、精确时长与 Time、全部 DAG 边、正时长操作的同引擎互斥，以及第 3 节的闭区间通信峰值和激活峰值。两个峰值分别计算后相加，不能改成同一时刻联合占用的峰值。

只有验证通过的完整候选可作为后续种子；全局答案仅在 Time 严格下降时替换。这样，一条探索分支失败、超出阶段预算或产生更差解，都不会把已经保存的可行答案覆盖掉。它保证本次运行各阶段之间的答案单调性，不保证在重新分配时间预算后，对每例都优于另一次独立运行。

## 9. 关键路径与资源顺序局部搜索

`full` 模式获得完整调度后，会尝试资源顺序局部改进。该阶段分成两段：**前缀**是在小例上先执行的有限轮次搜索，条件为 $J=10LB\le8000$；**扩展**则利用剩余时间继续搜索，对所有规模开放。两段采用相同的合法性和接受规则，预算不同。

### 9.1 把时间表变成资源链

固定 $P$、MAP、层布局和各操作时长。将每个卡组每类引擎上的正时长操作按执行顺序连成**资源链**：一条链边要求前一个操作结束后，下一个才能开始；通信链还可以附加一个时间单位的间隔。把资源链边加入模型 DAG 后，就同时表达了模型依赖和这一候选的引擎执行次序。

给定资源顺序后：

1. 拓扑排序检测是否成环。
2. 按拓扑顺序，用前驱结束时刻与所需间隔的最大值更新每个节点的开始时刻；这就是约束图上的最长路传播。
3. 分别考虑通信间隔 0、1。
4. 重新检查激活、通信缓冲的闭区间峰值。

最长路给出的完成时间来自一条关键路径，其长度包含操作时长和边上的必要间隔。局部搜索利用这条路径定位值得尝试重排的资源段。零时长操作保留在 DAG 和输出中，但不进入正时长资源链。最早重定时也可能因激活存活区间改变而违反内存，此时直接拒绝；代码没有穷举同一资源顺序下所有可能的延迟放置。

### 9.2 邻域与接受规则

搜索集中在关键路径相关资源段：

- 将操作在同一资源序列内前后移动 1 至 8 个位置。
- 对关键路径附近长度 4 至 7 的窗口尝试排列。

接受目标是二元组：

$$
\left(\operatorname{Time},\sum_o end(o)\right)
$$

的字典序下降：先比较 Time，较小者更好；Time 相同时，再比较全部操作结束时刻之和，较小者更好。第二项允许在 Time 持平时调整内部结构，为后续搜索提供新的邻域，同时不会恶化最终 Time。

短窗口排列只是局部枚举，不能理解为对整个用例完成了全局暴力求解。

### 9.3 有限前缀与按时间扩展

一次**候选评估**是对一组备选资源顺序进行重定时、目标比较和必要的内存检查。局部搜索先执行小例前缀：当 $J\le8000$ 时，最多进行 4 轮，每轮上限 3,000 次评估，并以统一计时起点后的 9 秒为截止点。前缀每轮从最新可行时间表重建资源顺序；没有接受移动时提前结束。

随后，`full` 模式下所有规模的完整调度都可进入扩展阶段。**一次扩展调用称为一个 pass**，每个 pass 最多进行 700 次候选评估，并从最新保留的时间表出发。程序在统一起点后 9200 毫秒的截止点前预留 30 毫秒；到达这条停止线后不再启动新的 pass。命令行 `--polish-pass-limit=N` 可以额外限制 pass 数，但不限制前面的最多 4 轮前缀，也不是把总评估数设为 $N$。

不同 pass 用变体编号轮换关键资源、关键操作、插入距离与块长度，并尝试移动 12、16、24、32 个位置。排列阶段还会改变长度 4 至 7 的访问次序。为避免总从相同的排列开头搜索，先给字典序下的排列编号，再通过阶乘数制解码从所选编号恢复一个起始排列，循环访问直到回到起点或耗尽当前调用预算。

每个 pass 的 700 次评估上限不保证穷尽长度 7 的全部 $7!=5040$ 种排列，插入等其他邻域也会消耗这份额度。所有被保留的候选仍须通过无环检查、Time/次目标比较和内存验证；变换访问次序不提供全局最优保证。

每次重定时都比较固定布局下的资源链最长路。若当前候选完成时间已经超过当前最佳解的 Time，该评估可安全停止，因为沿拓扑序传播的最大完成时间只会不降。

内存检查还有一条**快路径**，即先证明一个保守上界始终安全，再省略反复扫描。每组驻留内存固定；所有正时长通信操作位于同一资源链，闭区间最多有两个通信区间同时计数，故通信内存不超过 $2U$；激活区间总数不超过该组 $n_gB$，故激活内存不超过 $n_gBU_a$。只有固定驻留量与这两个上界之和不超过 $M$ 时，才可跳过该组的逐候选峰值扫描；其他组仍完整检查。全部组通过上界时，扩展阶段只需试零通信间隔，因为增加间隔只会增加资源链约束。

统一计时起点由 `solver::run` 在解析参数前记录，前缀的 9 秒与扩展的 9200 毫秒都从这个起点累计。这里采用**软截止**：程序在预定检查位置决定是否继续，已经开始的工作不会被外部计时器强行中断。因此，单次调用可能越过截止，最终运行限时仍由官方批量执行脚本保证。

## 10. 正确性保障、预算与复杂度

### 10.1 关键不变量

| 对象 | 保障方式 |
|---|---|
| 并行网格 | 枚举时检查专家整除、节点对齐与总卡数 |
| 切层 | DP、镜像构造和邻域移动均保持完整覆盖与非空块 |
| 专家数量 | 初始容量限制、两专家交换和负载配额组合都保持每 rank 恰好 $E/P$ 个 |
| 依赖 | 事件入度、列表前驱最早时间、局部 DAG 最长路 |
| 引擎互斥 | 每组双引擎状态、空档占用或资源链 |
| 内存 | 事件预留约束，或候选的闭区间峰值检查；新增候选统一复核两个独立峰值 |
| 完整输出 | 各调度内核生成全部操作；候选检查与官方 grader 核验 |
| 目标更新 | 常规严格降低 Time；局部重排允许次级目标下降 |

主要时长、内存、负载乘积和目标值使用有符号 128 位整数，避免用浮点近似决定时长、可行性和优劣。输出通过十进制转换保留整数值。

求解器内部筛选服务于各自搜索路径，最终独立验收仍以官方 grader 为准。给定 50 个用例的通过结果说明这些输出满足官方要求，不构成对任意输入都必定找到可行解的证明。

局部资源重排的时间评估有两种数值设置：`auto` 自动判断能否安全使用有符号 64 位整数，`wide` 始终使用有符号 128 位整数。这只是整数表示的选择，不改变调度规则。评估器先为每个节点预存时长，在候选评估中直接读取。

`auto` 的安全条件为：每个时长非负；令 `T_bound = 正时长总和 + J`，则最长无环路径至多含 $J$ 个节点且每条资源边间隔至多为 1，路径时长不超过 `T_bound`；`J × T_bound`、当前完成时间和次目标比较值均能由 64 位整数精确表示。`J × T_bound` 也覆盖所有节点结束时间之和。任何条件无法保证时，整次评估使用 128 位整数（代码类型名 `i128`），不截断数值。两种设置共用相同的拓扑传播、接受判据和候选生成；闭区间内存检查及内存乘法始终使用 `i128`。

这项时长预存和安全界计算是每次局部搜索调用开始时的一次 $O(J)$ 准备工作，不会在每个候选中重复展开。它位于初始截止检查之后，候选环节继续使用软截止；官方 50 例最大 $J$ 为 76,800。

### 10.2 统一时间预算

下表时间均从 `solver::run` 在解析参数前记录的起点累计，并非每阶段各自拥有相同额度。`full` 按阶段顺序使用剩余时间；其他搜索模式只运行第 4.1 节列出的阶段。

**小规模完整搜索**在前置精化结束时判定：模式为 `full`，$B\le16$、$J\le8000$，且当时 $L>G$。这是程序的固定分支条件，不随文件名切换。

| 阶段 | 小规模完整搜索 | 其余路径（按模式启用） |
|---|---|---|
| 候选生成、初始精化、窗口和专家组合 | 固定枚举与访问预算；前置步骤没有统一截止覆盖 | 相同 |
| 常规列表搜索 | 累计 3.4 秒截止 | 累计 8 秒截止 |
| 额外布局与基础波前 | 累计 4.2 秒截止 | 累计 9 秒截止 |
| 资源下界布局搜索 | 最多 2.0 秒，且不超过累计 6.1 秒 | 不启用 |
| 优先级重建与非均匀间距 | 最多 1.6 秒，且不超过累计 7.8 秒 | 不启用 |
| 局部搜索前缀 | 满足节点条件时最多 4×3,000 次评估，累计 9 秒截止 | 相同，且只在 full 中启用 |
| 局部搜索扩展 | 每次最多 700 次评估，累计 9200 毫秒截止前 30 毫秒停止开启下一次调用 | 相同，且只在 full 中启用；不设 $J$ 门槛 |
| 官方 runner | 每例外部限时 10 秒 | 相同 |

新增阶段以“进入时刻 + 本阶段额度”和“累计上限”的较早者为截止。前序阶段提前结束，后续可以提前开始；没有剩余时间则直接跳过。布局搜索内部把预算划为准备、DP、真实调度评估三个部分，按 $P$ 分配工作并轮流评估；排序搜索再按去重布局数分配剩余时间。参数扫描和偏移精化也分开限额，避免前一个子阶段吞掉整个预算。

单次调度与校验仍是协作式的软截止，不能被内部计时器即时打断；折返 DP 则在有界转移块之间主动检查。前置步骤和已经开始的工作可能跨过截止，因此不能仅凭 9.2 秒配置证明任意输入都在 10 秒内结束。实测墙钟与超时数见第 12 节。

### 10.3 分阶段复杂度

记 $J=10LB$，$Q$ 为合法 $P$ 的数量，$V_P=\min(L,64,\lfloor R/P\rfloor)$。DAG 的边数为 $O(J)$。

| 阶段 | 时间上界或主要成本 | 主要工作空间 |
|---|---|---|
| 固定 $P$ 的专家映射 | $O(L(E\log E+EP+6(E^2+P\log P)))$ | 映射 $O(LE)$，逐层临时数组 $O(E+P)$ |
| 固定 $P,V$ 的切层 DP | $O(VL^2)$ | $O(VL)$ |
| 全部初始切层 DP | $O(\sum_P V_P^2L^2)$ | 单次 DP $O(\max_PV_PL)$，另存候选映射 |
| 资源下界连续 DP | $O(HL^2+GL^2)$，$H$ 是采样门槛组合数 | $O(HL+GL+L^2)$ |
| 资源下界折返 DP | 缓存成本 $O(HL^4)$，转移最坏 $O(GL^4)$；实际按截止截断 | $O(\binom{L+1}{4}+GL^2+HL)$ |
| 一次事件调度 | $O(JG+J\log J)$ | $O(J)$ |
| 一次普通列表调度 | 图遍历及堆操作为主要成本；`early` 选点方式另有重入队 | $O(J)$ |
| 带填空的列表调度 | 空档线性扫描与数组移动最坏可达 $O(J^2)$ | $O(J)$ |
| 一次闭区间内存检查 | 各检查路径的安全上界为 $O(JG+J\log J)$；包含逐组扫描与端点排序 | $O(J)$ |
| 一次局部顺序评估 | 重建资源约束、拓扑传播与内存校验，$O(JG+J\log J)$；通过严格内存上界的组可省去逐候选峰值扫描 | $O(J)$ |
| 专家类型组合搜索 | 配额组合枚举与 DFS，最坏为组合级；由访问预算截断 | 配额表、记忆状态及递归栈 |

专家交换中，排除两个被交换 rank 后寻找第三方最大负载，最多检查已排序 rank 列表的前三项，因此单对交换无需完整扫描 $P$ 个 rank。

DP 对每一个 $V$ 都重新建表，不能把整个候选生成写成一次 $O(V_PL^2)$。事件调度还包含逐轮扫描全部卡组和准入检查，所以不能省掉 $JG$ 项。列表调度的具体耗时受重入队次数影响；带填空时，也不能统一宣称为 $O(J\log J)$。

局部搜索每次调用构建基础 DAG、按当前排程生成关键路径邻域；每次邻域评估重新准备入度与资源链，再做拓扑传播。未通过严格内存上界的卡组仍扫描全部 microbatch 和层并排序端点，产生 $O(JG+J\log J)$ 成本；通过上界的卡组跳过逐候选扫描。小例前缀最多 12,000 次评估，扩展为不限总评估次数的有截止时间循环，每次调用最多 700 次；因此复杂度受实际候选数和软截止控制，不能用固定 12,000 次描述所有规模。

总搜索成本还要乘以实际候选数。保存全部 $P$ 的代表 MAP 需要 $O(QLE)$ 空间；多份探测调度和当前候选可同时存在，因此整个程序的峰值内存也高于单个调度内核的 $O(J)$。

### 10.4 适用边界

算法利用了少种类重复负载、有限合法并行规模、较小层数、双引擎独立性以及权重梯度可延后的结构。其结果不附带全局最优性保证，主要限制为：

- 初始切层 DP 优化代理负载；资源头尾 DP 优化采样下界。两者都不直接优化完整调度的 Time，每个 $P$ 只保留少数布局进入真实调度搜索。
- 折返 DP 受缓存上限与阶段预算限制，未完成全部组数时不宣称已经找到了该下界目标的全局最小布局。
- 专家组合查询和资源顺序邻域都受预算约束。
- 搜索截止依赖机器负载，接近限时时实际完成的候选数可能改变。
- 验收结论针对给定 50 个最终用例，不外推为任意分布上的性能保证。

## 11. 软件设计、模块与运行接口

前面的章节解释了算法如何产生答案；本节解释它如何组织成可维护的程序。这里的**设计模式**是分配代码职责、约定对象协作的方法，与第 2.3 节决定操作排序的“调度模式”不同。当前工程采用策略、适配器、门面三种模式，并用参数对象整理接口。

### 11.1 设计模式及其协作

#### 11.1.1 参数对象：让一次调度调用表达清楚

一次调度需要三类信息：确定的问题数据、准备尝试的规则，以及接收结果的位置。把这些信息分开，可以避免调用处出现一长串容易错位的整数和布尔参数。

| 对象 | 保存的内容 | 数据归属 |
|---|---|---|
| `ProblemView` | 微批次数、层数、卡组数、层到组映射、逐层时长、每组层数 | 大向量用只读引用访问，数据由调用方持有 |
| `EventConfig` | 激活容量、通信缓冲、窗口、事件优先级及奖励等设置 | 数值按值保存，容量与缓冲数组由调用方提供 |
| `ListConfig` | 窗口、排序变体、填空、波前、随机键及非均匀微批次偏移 | 标量按值保存，非均匀偏移向量由配置对象持有 |
| `ScheduleOutput` | 操作向量和完成时间；列表内核可选输出的开始、结束时刻数组 | 引用调用方的结果存储，不再包一份完整答案 |

`ProblemView` 是**非拥有视图**：它提供访问入口，不负责保存所引用数据的生命周期，调用方必须保证数据在调度调用期间有效。`EventConfig` 的激活容量与通信缓冲数组也必须有效。参数对象是接口整理手段，不把每个结构体都算作一种设计模式。

列表排序通过 `ListRankMode` 的具名枚举区分波前、DAG 时长、随机键与非均匀偏移。`ListConfig` 扩展配置而继续使用同一个列表策略，避免为了每种排序公式另造调度器类。`SearchBudget` 把列表截止、波前截止、布局额度与排序额度放在同一个值对象中；门面负责把它们换算成绝对时刻，搜索模块只负责在传入截止前探索。

#### 11.1.2 策略与适配器：选择算法，接入内核

**策略模式**把可选择的算法放到统一调用约定后面，使调用组织与具体算法分开。本工程使用编译期选择：`Scheduler<Strategy>` 保存问题视图，其 `run(config, output)` 调用由模板参数指定的策略。

具体策略为 `EventScheduleStrategy` 和 `ListScheduleStrategy`，分别对应事件与列表内核。每个策略声明自己的 `Config` 类型，并提供 `schedule(problem, config, output)`。调用形状相同，配置仍保持各自的类型；选择策略发生在编译时，不依赖运行时的虚函数查找。

**适配器模式**解决两边接口形式不同的问题。两个具体策略同时承担适配职责：把 `EventConfig` 或 `ListConfig` 的具名字段按正确顺序交给底层调度函数。调度内核继续负责建图、事件推进、排序和放置；适配层只连接接口，不复制一份算法。

还需区分策略类型与策略内部的配置：`Scheduler<EventScheduleStrategy>` 选择事件内核，而其中的 `EventConfig.mode=0/1/2` 选择该内核的优先级规则；命令行 `--mode=full/list/event/serial` 决定哪些搜索阶段会发起这些调用。

一次列表候选的实际调用过程为：

1. 搜索模块准备固定的问题视图，并给 `ListConfig` 的窗口、排序等字段赋值。
2. `Scheduler<ListScheduleStrategy>::run` 转发一次完整调度请求。
3. `ListScheduleStrategy` 将字段适配到列表内核的参数，内核写出操作向量和完成时间。
4. 搜索模块按本阶段的规则筛选并检查结果，必要时更新当前最佳解。

事件与列表内核共用 `solver::ScheduledOperation` 操作类型，列表结果可以直接进入后续校验，避免逐项转换。普通列表搜索在原有位置先检查返回的完成时间，再决定是否做内存检查；波前搜索则在调度后按自己的流程执行安全检查。两条路径保留各自的处理次序。

新增策略时，实现其 `Config` 与 `schedule` 约定，再在需要使用它的搜索位置选用 `Scheduler<NewStrategy>`。上下文无需为新算法增加分支；候选如何枚举、何时调用新策略，仍由搜索模块决定。可编译的接口替身见[策略注入检查](../../scripts/test_strategy_api.cpp)，它只验证接口可接入，不提供一张可提交的时间表。

#### 11.1.3 门面：分开求解流程与命令行输入输出

**门面模式**向调用方提供一个清楚的求解入口，由它协调内部多个模块。当前门面是 `Solver::solve`：接收已解析的 `InputData`、`Options`、统一计时起点和结果引用，按第 4 节的阶段顺序求解。找到结果时把完整方案移动写入结果对象并返回成功；无可行配置时返回失败。

`solver::run` 负责外部边界：记录计时起点、解析参数、打开输入、调用门面、处理错误并输出答案。计时起点仍在解析参数之前，因此提取门面没有为各阶段重新开始计时。入口到算法的关系是 `main → run → Solver::solve → 各搜索模块`，结果沿调用关系返回后由 `run` 序列化输出。

#### 11.1.4 这些设计如何约束运行开销

抽象放在一次完整调度或一次完整求解的边界。问题视图引用现有向量，结果按引用写入；策略选择由模板完成，不在节点、事件或优先队列循环中增加虚函数调用。这样的结构使新增算法接口、排查参数和复用求解入口更清楚，但性能结论仍以验证为准。

新的偏移配置会复制至多 $B$ 项的向量，多布局搜索也会保存少量完整种子；这是算法所需状态，不应把“接口使用引用”误解为整个搜索零复制。实际性能以本轮完整验收为准。`--polish-pass-limit` 仅约束末段局部扩展次数，无法使前面的截止式布局和排序搜索变成固定工作量测试。设计参与者与类关系图另见[设计模式说明](../design-patterns.md)。

### 11.2 源码结构

维护代码按职责拆分为多个 `.cpp` 实现与 `.hpp` 接口/值类型。各 `.cpp` 分别编译为对象文件，`src/solver.cpp` 只定义全局 `main`，顶层流程位于 `src/app/solver.cpp`。`src/sources.mk` 是构建和单文件导出共用的唯一源清单。`make submission` 可选地生成自包含裁判件；它与多翻译单元构建共享模块源码，但不要求二进制逐字节相同。

| 文件 | 职责 |
|---|---|
| `src/common.hpp`, `src/core/operation_graph.hpp` | 标准依赖、操作与引擎的协议定义、节点编码及 inline DAG 边模板。 |
| `src/model/problem.hpp`, `src/model/scheduled_operation.hpp` | 输入、候选、调度结果和操作值对象；模型不依赖内核实现。 |
| `src/io/{numeric,input,options,output}.hpp/.cpp` | 数值工具、输入、选项和输出的声明/实现。 |
| `src/placement/{expert_mapping,grouped_placement}.hpp/.cpp` | 专家映射与时长模型，以及分组 placement 搜索。 |
| `src/scheduling/schedule_api.hpp` | 调度问题/配置/输出视图及编译期策略调用约定。 |
| `src/scheduling/{event_scheduler,list_scheduler}.hpp/.cpp` | 事件调度及列表/波前调度内核与具名接口适配器。 |
| `src/search/limits.hpp` | 搜索时间/数量预算、数值分母和无穷大哨兵。 |
| `src/search/{candidate_search,layout_search,initial_search}.hpp/.cpp` | 初始候选、布局评估与当前最佳解选择。 |
| `src/search/{window_search,window_borrow,boost_search,placement_search}.hpp/.cpp` | 窗口、借用、奖励和专家放置搜索。 |
| `src/search/{list_search,wave_search}.hpp/.cpp` | 列表与波前搜索阶段。 |
| `src/search/layout_bound_search.hpp/.cpp` | 资源头尾模型、连续/折返 DP、镜像邻域、插值及布局种子管理。 |
| `src/search/priority_search.hpp/.cpp` | 扩展波前、随机优先级及非均匀微批次偏移搜索。 |
| `src/search/schedule_validation.hpp/.cpp` | 新增候选共用的网格、MAP、DAG、资源和闭区间内存校验。 |
| `src/search/{local_engine_polish,polish_driver}.hpp/.cpp` | 资源顺序局部搜索及阶段预算编排。 |
| `src/app/solver.hpp/.cpp` | `solver::run` 处理输入边界，`Solver::solve` 编排顶层搜索流程。 |
| `src/solver.cpp` | 全局 `main`，调用 `solver::run`。 |
| `src/sources.mk` | 构建与 amalgamate 共用的唯一实现文件清单。 |
| `submission/solver.cpp` | 通过 `make submission` 可选生成的自包含裁判源文件。 |

操作语义编号、共享 DAG 边顺序及常量保留理由见[模块设计说明](../module-design.md)。操作数组和输出名称表按同一枚举顺序排列；共享 DAG 构造函数保留边插入次序，使同优先级节点仍按确定的次序处理。预算、分母和无穷值使用带单位/语义的常量；数制基数、公式系数、启发式候选顺序和哈希混合常量按原意保留。

项目格式要求见[编码规范](../coding-style.md)与[格式配置](../../.clang-format)：四空格缩进、控制语句加花括号，类型、函数采用各自一致的命名方式，并保留便于对照公式的问题域符号。

### 11.3 构建与单例验证

在仓库根目录编译维护源码并可单例验证：

~~~sh
make -j2 build
./build/solver data/official/Problem/cases/x18_vl_tight_small.txt > /tmp/x18-current.out
python3 data/official/Problem/grader.py \
  data/official/Problem/cases/x18_vl_tight_small.txt /tmp/x18-current.out
~~~

默认 Makefile 构建从 `src/sources.mk` 读取源清单，将各实现编译到 `build/obj/*.o` 并生成 `.d` 依赖文件，再通过链接时优化（LTO）生成 `build/solver`。`make -j2 build` 支持增量构建；`scripts/build.sh` 调用同一目标。编译与链接选项为 C++17、`-O2`、`-pipe`、`-Wall`、`-Wextra` 和 `-flto`。

生成并检查单文件裁判提交件：

~~~sh
make submission
make submission-check
g++ -std=c++17 -O2 -pipe -Wall -Wextra submission/solver.cpp -o build/solver-submission
~~~

导出器按 `src/sources.mk` 的顺序拼入实现，并递归展开 `src/` 内的本地头文件；标准库 include 保留，为模块添加 begin/end 注释并去除 `#pragma once`。越界、缺失或不支持的 include 会报错。输出不含时间戳，可由 `make submission-check` 检查是否与模块源码一致。该单文件是可选提交形式；普通编译器编译该文件不需要 LTO，且不要求与联合构建二进制逐字节一致。

答案写入标准输出，搜索诊断写入标准错误。输出依次包含 `V P`、`PSI`、`MAP` 和 `SCHEDULE`。调度中每个操作一行，按开始时刻排序，条目为 `时刻 microbatch:层:操作名`。答案文件不另写一个 Time 字段，官方验收器根据时间表计算它。

### 11.4 命令行：五个选项与一个可选输入路径

程序只公开以下 **5 个选项**。带值的选项使用 `--名称=值` 形式；选项后的数值或模式名不是新的独立开关。

| 选项 | 允许值与默认值 | 控制什么 |
|---|---|---|
| `--mode=...` | `full`、`list`、`event`、`serial`；默认 `full` | 选择第 4.1 节定义的搜索阶段组合 |
| `--force-p=N` | 非负整数；默认 0，表示不限定 | 只在合法并行规模集合中选择指定的 $P$；指定值不可行时报告无可行配置 |
| `--retime-mode=...` | `auto` 或 `wide`；默认 `auto` | 选择第 10.1 节的局部重定时整数评估路径 |
| `--polish-pass-limit=N` | 非负整数；默认 0，表示只受时间截止限制 | 限制第 9.3 节的局部扩展 pass 数，不限制前缀轮数，也不是候选评估次数 |
| `--help` | 无值，别名为 `-h` | 显示帮助并退出，不读取用例 |

正常求解只需提供输入文件，默认就是 `full`。`retime-mode` 和 `polish-pass-limit` 用于数值或固定工作量诊断；只有 `full` 会进入它们控制的局部重排阶段，在 `list/event/serial` 中设置这两项不会增加搜索阶段。`--polish-pass-limit=0` 也不会取消 9200 毫秒的固定预算。

输入文件是**位置参数**，不计入五个选项。最多指定一个，位置可以在选项之前或之后；省略文件或使用 `-` 时从标准输入读取。典型命令为：

~~~sh
# 默认完整搜索
./build/solver data/official/Problem/cases/x18_vl_tight_small.txt > answer.txt

# 在列表搜索结束后输出，观察该搜索范围的结果
./build/solver --mode=list data/official/Problem/cases/x18_vl_tight_small.txt > answer-list.txt

# 限制局部扩展调用数，用于固定工作量对照
./build/solver --polish-pass-limit=24 data/official/Problem/cases/x18_vl_tight_small.txt > answer-fixed.txt

# 查看帮助
./build/solver --help
~~~

例如，`--mode=list` 选择整个流程的搜索范围，`--retime-mode=wide` 选择整数表示，而 `EventConfig.mode=1` 是代码内部的一次事件调度配置；三者不会相互替代。内部窗口、奖励和排序组合由搜索阶段管理，不再逐项暴露为命令行开关。

正常参数解析遇到未知选项、非法枚举值、负数或带额外字符的数值、重复输入路径时，会输出错误并退出 2；无法打开输入或缺少必要输入字段也会报错。`--help` 是立即退出的帮助请求。输入题目数据仍应遵循官方格式，不依赖求解器替代官方输入验证。

### 11.5 官方验收与辅助检查

直接使用官方批量验收器：

~~~sh
python3 data/official/Problem/run_all.py --cmd "./build/solver" --timeout 10
~~~

该脚本把用例路径追加到命令行，而不是重定向标准输入。它也不通过 shell 执行 `--cmd`，所以不能直接把 `< {case}` 写进该参数。

也可通过以下项目入口执行同一官方验收：

~~~sh
make official
~~~

该命令通过未修改的 `data/official/Problem/run_all.py` 串行处理官方 50 例；最终全量验收以其原始输出为准。`scripts/run_acceptance.sh` 是开发用辅助脚本，可保存逐例输出：

~~~sh
./scripts/run_acceptance.sh current_report_check full ''
~~~

三个位置参数依次为：结果目录名、搜索模式（`full|list|event|serial`）和用例正则过滤器。结果写入 `results/<目录名>/`；每例保留答案、诊断、checker 诊断和汇总行。该辅助脚本用位置参数向求解器传递用例路径，先用 10 秒限时运行求解器，再调用官方 grader；它不替代官方全量 runner。

本轮为同时保留逐例搜索诊断，官方 runner 的 `--cmd` 使用 `scripts/capture_solver_run.py` 包装真实求解器。包装器每例实际执行一次 `build/solver`、保存输出并原样转交给官方判题，绝不回放已有答案。官方 10 秒墙钟包含包装器启动和保存记录；包装器另在 9.75 秒终止仍未结束的子进程并返回失败，防止外层超时后留下继续运行的子进程。完整命令见第 12 节。

新增模块的独立检查入口为：

~~~sh
./scripts/test_search_modules.sh
make options-check strategy-check
~~~

布局测试在 $L=8$ 上穷举所有合法切点，逐组数对照连续和折返 DP；另检查组合缓存编号无碰撞、镜像移动保持组层数、实际切分与初始候选切分不一致的边界、插值和缓存上限。排序测试核对均匀偏移与时长波前的一致性，并检查乱序种子归一化、$K<L$、坏切分、非法网格、重复/缺失操作、依赖、引擎冲突和内存等边界。它们验证具体算法性质，官方 50 例仍负责最终答案验收。

### 11.6 4+1 架构视图

**4+1** 用四个结构视角和一个场景视角解释同一系统：逻辑视图关注领域概念与功能，开发视图关注模块与构建，进程视图关注运行时协作，物理视图关注部署位置；“+1”通过具体用例把前四者连接起来。

| 视图 | 当前程序中需要说明的关系 |
|---|---|
| [逻辑视图](../../.archify/architecture-suite-integration-20261031-085057/logical/index.html) | 输入与候选确定布局、映射及操作时长；DAG、引擎和内存约束共同决定可行调度，Time 衡量调度质量。 |
| [开发视图](../../.archify/architecture-suite-integration-20261031-085057/development/index.html) | 入口、I/O、模型、专家映射、调度内核和搜索模块按职责组织；共同源清单支持多文件编译与可选单文件导出。 |
| [进程视图](../../.archify/architecture-suite-integration-20261031-085057/process/index.html) | `run → Solver → 搜索/内核` 在同一求解进程内同步执行；官方 runner 等求解结束后再启动 grader。 |
| [物理视图](../../.archify/architecture-suite-integration-20261031-085057/deployment/index.html) | C++ 可执行文件与 Python 验收程序在本机运行；题目和临时答案通过本机文件系统交接。 |
| [场景视图（+1）](../../.archify/architecture-suite-integration-20261031-085057/scenarios/index.html) | 默认求解、限定候选、帮助、输入错误、无解、进程超时和答案不合法分别经过对应模块与边界。 |

这里的**进程**是实际运行的程序实例，与题目中的计算/通信引擎不同。求解器在 CPU 上串行搜索，输出可以安排多组引擎并行的调度表，但不实际运行 GPU 训练。进程图的纵向位置只表示先后顺序，不表示测量时长；Time、求解 CPU 和墙钟的区别仍按第 1.3 节解释。

四种命令行搜索模式决定哪些阶段参加；事件内核的数字调度模式决定操作优先级；软件设计中的静态策略则决定调用哪种调度实现。这三个层次分别对应第 4.1、2.3 和 11.1 节。完整场景对应表、模块依据与部署解释见[4+1 视图说明](../architecture-4-plus-1.md)。
