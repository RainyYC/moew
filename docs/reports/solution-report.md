# 解题报告：满足内存约束的 MoE 分块与重叠吞吐优化

## 1. 赛题理解

### 1.1 问题概述

给定集群拓扑（节点数 N、每节点卡数 S，总卡数 R=N·S）、每卡 HBM 上限 M、模型规模（L 个 MoE 层、每层 E 个可路由专家、top-k 路由）与逐层负载分布，输出一份完整映射：

- **网格** (V, P, D)：V 个管线 stage、P 路专家并行、D 路数据并行，满足 V·P·D=R；
- **切层** ψ：L 层连续切为 V 段；
- **专家放置** σ（MAP）：每层 E 个专家放到 P 个 rank，每 rank 恰好 E/P 个；
- **整步调度** SCHEDULE：所有 microbatch 在一个训练步内的十类操作时间表。

目标是使一步训练的 wall-clock time 最小，且每张卡的内存不超过 M。本题不要求精确最优解，评测器只按规则前向模拟判分，鼓励在时间预算内搜索更优映射。

### 1.2 关键机制（模型事实）

- **十个操作**：每 (microbatch, 层) 有前向 4 个（s→disp→gemm→comb）与反向 6 个（s_bwd→comb_bwd→gemm_dx→gemm_dw→disp_bwd→s_dw），依赖顺序固定。s/gemm/s_bwd/gemm_dx/gemm_dw/s_dw 占用**计算引擎**，disp/comb/comb_bwd/disp_bwd 占用**通信引擎**。
- **引擎互不冲突**：每个 stage 独占一套计算引擎和一套通信引擎，两类引擎可同时工作，这是全部重叠收益的来源。同一 stage 同一时刻内不得有两个计算操作或两个通信操作。
- **单个 microbatch 无法自重叠**：四段严格依赖，只能靠不同 microbatch 与不同 stage 交错获得重叠。
- **计算看最慢 rank**：层 l 的计算时长由该 stage 内承载 slot 数最多的 rank 决定 ml=max_r L_{l,r}，偏斜负载下 MAP 的放置直接决定 ml。
- **通信按对端类型计**：一次 AllToAll 时长 x = max(pin·X/Bin, pout·X/Bout)·Fio，其中 X = ceil(T·H·(P-1)/P)，H=⌊d·b/k⌋；同节点流量走 Bin、跨节点走 Bout。EP 组与节点对齐由 P|S 或 S|P 保证。
- **内存三块**：Mexp（静态专家参数，(E/P)·Z+Zs 每层每卡）+ Movl（通信缓冲，U × 同时未完成通信操作数峰值）+ Mact（激活，Uact × 前向完成未反向的 (mb,l) 峰值），三者之和 ≤ M。

### 1.3 决策耦合与优化本质

三个决策互相纠缠：P 决定每卡驻留专家数与通信流量，V 与 ψ 决定共卡层数与最慢 stage，调度决定重叠程度与内存峰值。目标时间由「最慢 stage 的计算链」「最挤的通信链」与「跨 stage 的管线链」的最大值决定，是典型的 min-max 型瓶颈优化。

## 2. 方案设计

### 2.1 总体框架

在 (P, V, D, W) 网格上搜索，对每组参数快速构造一份调度并调用模拟器校验，保留 Time 最小的合法解。流程：

```
for P in 合法专家并行度:
    计算各层时长 / 计算权重 C / 通信权重 Wc / 每层内存
    for V in 合法 stage 数 (RP % V == 0):
        ψ = dp_split2(L, V, C, Wc)          # 均衡切层
        内存可行性检查（Mexp + U + 最大激活预算）
        w_max = 窗口上限（由激活内存约束推出）
        for W in 候选窗口（含 1 和 w_max，从大到小）:
            sched = build_schedule(...)     # 贪心列表调度
            模拟校验 → 更新 best
```

### 2.2 专家放置 greedy_map

按每层负载偏斜度处理：

- 负载均衡的层：顺序放置（每 rank E/P 个）。
- 偏斜层：按专家负载降序，逐个放入当前承载最少的 rank（且受每 rank 恰好 E/P 个的容量约束）。这相当于贪心地均衡各 rank 的 slot 总和，压低 ml。

### 2.3 层切分 dp_split2

把每个 (microbatch, 层) 的时长分解为计算因子 `cf = 1+α(1+β)` 与通信因子 `kf = 2(1+α)`（α、β 为反向系数），定义每层权重：

- 计算权重 C_l = cf·(s_l + gemm_l)
- 通信权重 Wc_l = kf·x_l

对 V 段做 DP，目标是最小化所有 stage 中 max(ΣC, ΣWc) 的最大值（即最慢 stage 的上下界），回溯出切点。相比只按 ΣC 切分，该目标同时压低计算与通信两条链。

psi_candidates 在此基础上无条件追加**按层数均分的 balanced_split**（及 ±1/±2 微移）作为候选：内存受限场景下负载均衡的 DP 切分可能把过多层塞进同 stage 导致 Mexp 超限，而均分切分能保证「每 stage 层数最平均」的可行选项永远在候选集内（见 §4 第 14 条）。

### 2.4 调度生成 build_schedule

事件驱动的贪心列表调度器（Dijkstra 风格），为每个操作维护前驱计数：

- **前向链**：s→disp→gemm→comb→（同 stage 下一层 s / 下一 stage 首层 s）。stage v 首层 s 额外依赖前一个 stage 末层 comb，且受 1F1B 窗口 W 约束（mb≥W 时需等待 mb-W 在该 stage 的反向完成）。
- **反向链**：s_bwd→comb_bwd→gemm_dx→gemm_dw→disp_bwd→s_dw→（同 stage 前一层 comb，从而释放该层反向）。s_bwd 需等本 stage 前向完成。
- **资源互斥**：每个 stage 维护 [comp_free, comm_free] 两个引擎空闲时刻，操作在 max(依赖就绪, 引擎空闲) 开始。
- **窗口 W**：mb 在 stage v 的反向全部完成后释放 mb+W 在该 stage 的首层前向，实现 1F1B 式内存受限的重叠。

堆的优先级让前向操作先于反向操作出队（isf 键），使反向尽量后置、前向尽量铺开，与 1F1B 的「先填满前向、再交替反向」直觉一致。

**调度变体（variant）**：堆键中再叠加三组方向开关 `(fwd_bias, mb_desc, l_desc)`——前向优先还是反向优先、microbatch 递增还是递减、层号递增还是递减。同一配置可生成多种不同拓扑的调度，取其中校验通过且 Time 最小的。粗筛阶段用 2~3 个变体、精筛与最终细化用 5 个变体。

### 2.5 内存约束与剪枝

- **Mexp**：每个 stage 的层数 × ((E/P)·Z+Zs)，超限直接跳过该 (P, V)。
- **激活上限 w_max**：对每个 stage，由 (M − Mexp − U) / (层数·Uact) 推出允许同时活跃的最大 (mb,层) 数，窗口 W 不得超过该值；由此保证 Mact ≤ M。
- **下界剪枝**：任选一个 W 调度得到 best 后，后续 (P, V) 若 `nmb·max_v max(ΣC_v, ΣWc_v)` ≥ best 则跳过（这是每个 stage 串行执行所有 mb 的乐观下界，实际只会更大）。

### 2.6 搜索流程（coarse → refined → global refine）

两阶段搜索，全部操作在 time_budget 内随时可被截断：

1. **粗筛**：对每个 (P, V, ψ)，尝试小窗口集 W∈{1,2} 与 2~3 个变体，取每个配置的最好结果进入 coarse 列表。
2. **精筛**：coarse 中前 5 个（res ≤ best×1.1 的）配置，先扫远窗候选 `{w_max, nmb, nmb/2, nmb/4, 32, 24, 16, 12, 8, 6, 4, 3, 2}`（默认变体），再做**稠密升序窗口扫描**：从 W=1 逐窗尝试，连续 3 个 W 无改善即提前终止（W 与 Time 通常单调劣化或先降后升，该策略既能覆盖小窗口的最优点，又不会在大窗口区浪费算力）；最后在最优 W 的 ±1、±2 邻域上换全部变体搜索。
3. **全局细化**：若 best 配置未被精筛覆盖，用全变体 + 更密的 W 集（大规模收窄为 `{1,2,4,8,16,w_max}` 与 2 个变体）再搜一轮，锁定局部最优窗口。
4. **随机收尾**：对 best 配置，在最优 W 及其 ±1/±2 邻域上追加若干随机变体（`(fwd_bias, mb_desc, l_desc)` 随机组合，小规模 10 个、大规模 5 个，用固定随机种子保证可复现）。校验器加速后搜索通常远早于预算收敛，这部分用空余时间换取对未知测试点更广的调度拓扑覆盖，成本极低。

窗口 W 与 Time 的关系通常非单调（W 小则内存安全但流水线气泡多，W 大则前向铺开更开但会挤乱通信/计算交错），因此用「候选集 + 稠密扫描 + 邻域微调」而不是二分。

### 2.7 校验器 sim.py

实现题面第 4 节的完整模拟，并对热路径做了针对性加速（详见 4 节第 9 条）：

- 校验网格、PSI 严格递增、MAP 计数合法；
- 事件预解析：所有操作 token 先一次性解析为 `(mb, layer, oi)` 整数元组（字符串 token 与求解器直接传入的元组 token 统一处理），调度循环内不再做字符串切分；
- 依赖检查分为**暂态阻塞**与**永久阻塞**：依赖尚未被调度（comp_end 为 -1）时暂缓，下一轮可能被同时刻的零时长前驱满足；而依赖已完成但结束时刻 > 当前时刻 t，或引擎被占用到 t 之后，属于永久阻塞——comp_end 与引擎空闲时刻在该时刻内只会单调增大，这类操作无论如何都无法在 t 起步，直接判非法，避免反复重扫；
- 引擎互斥：非零时长操作必须等引擎空闲；**零时长操作不占用引擎**（这是模拟中的一个关键细节，见 4 节）；
- 用扁平数组（`comp_end` 按 `(mb*L+layer)*10+oi` 线性索引、`fwd_end`/`layer_fwd_end`/`layer_bwd_end` 同理）替代字典与单元素列表，消除散列开销；
- 内存重叠峰值改用排序合并扫描（`_max_overlap`），把逐点双循环的 O(n²) 降为 O(n log n)；
- 返回最大完成时刻作为 Time。

加速效果：big4（64 卡、nmb≈1280）单次校验从约 2.4s 降至约 0.2s（约 12 倍），big4 全搜索从约 71s 降至约 13s，所有 10 个测试点结果完全不变。

## 4. 关键问题与修复记录

1. **输入按行解析**：层负载向量与下一行可能同行，token 流式解析会产生歧义；改为按行解析，`Tl` 或 `Tl a0...aE-1`。
2. **同层拓扑序**：同一时刻同一 stage 的多个操作（如 s 与 gemm 同行的样例 5）必须按依赖拓扑序处理，用 pending 循环逐轮推进未满足依赖的操作。
3. **零时长操作不占引擎**：样例 2 中 gemm=24 与 s=0（时长 0 的 gemm_dw 等）同 stage 同时刻并发，说明零时长操作不应占用计算引擎，模拟器据此实现。
4. **调度器完整性 bug**：早期版本只在前向 comb / 反向 s_dw 处递减剩余计数，导致反向链部分操作永远不被调度；修正为每个操作调度时都递减对应计数。
5. **greedy_map 容量约束**：未限制每 rank 恰好 E/P 个专家会导致 MAP 非法（计数不等）；加入 rank_cnt 容量限制后合法。
6. **Pyright 类型告警**：`best` 初值为 None 且仅在闭包内赋值，类型推断为 Never；显式标注 `Optional[Tuple[int, str]]` 解决。
7. **调度变体堆键 bug**：`hkey` 为支持 mb/层号升降序把 `-mb/-l` 放进堆键，但出堆时按原字段解包，导致 mb_desc/l_desc 变体产生越界操作。修复为把真实 (mb, l) 作为堆键的载荷字段，排序键单独存放。
8. **全局细化耗时**：初版对 best 配置做「全 W × 全变体」的最终扫描，big4 单次校验约 2.7s，导致总时长超过预算。修复为：best 配置若已在精筛覆盖则跳过；大规模下 W 候选与变体数收窄。
9. **校验器加速**（本次主要优化）：原 validate 在事件循环里对每个 token 反复做字符串解析、OIDX 字典查找、`list(pending)`/`pending.remove()` 重扫，且把「永久阻塞」（依赖结束时刻或引擎空闲时刻大于当前 t）当作暂态反复暂缓，big4 单次校验约 2.4s。重写为：① 事件一次性预解析为 `(mb, layer, oi)` 整数元组；② 依赖为 -1 才暂缓，依赖已结束在 t 之后或引擎忙到 t 之后直接判非法；③ 全部状态改用扁平数组；④ 内存重叠峰值改用排序合并扫描。big4 单次校验降至约 0.2s（约 12 倍），全搜索 71s→13s，10 个测试点结果零变化。
10. **模型边界复核**：逐条对照官方样例校准——零时长操作不占引擎（样例3）、引擎在相等时刻释放（ex1）、X=⌈T·H·(P-1)/P⌉ 公式正确（正文数值为笔误）、无跨 stage 反向依赖（样例5）、D 不拆分 microbatch（样例3）。
11. **大样例收敛验证**：对 big1-4 追加切分穷举 / 随机调度 / 切分扰动搜索，全部收敛于既有解，无更优。
12. **ex2/ex6 全局最优**：先手工排程把 Time 压到 4040/1460（关键是把下一 mb 前向插入当前 mb 反向尾部之前、comb/comb_bwd 提前），再用穷举搜索证明为 (V=2,P=2,D=1) 网格下全局最优：每 stage 内两个 mb 的十步链交错共 C(20,10)=184756 种，按「依赖就绪+引擎空闲」紧下界模拟，两 stage 仅经 feed 耦合，对全部 feed 对求整体 min 即最优（opt_stage.py/opt_joint.py）。该路径已内建进求解器。
13. **内存感知切层**：psi_candidates 无条件追加按层数均分的 balanced_split，保证内存均衡切分永远在候选集内（big2 的 P=2/V=8 因此可评估，仍劣于 P=1）。
14. **s 项主导性量化**：大样例 s/s_bwd/s_dw 三项（不随 P 分摊）占计算量 71%~83%，坐实「P=1 最优」。
15. **大样例利用率复核**：瓶颈 stage 忙 95%~98%，间隙全部来自流水线填充/排空与首尾依赖，非调度松弛。
16. **W 软约束评估 + 穷举内建**：评测器不强制 1F1B 窗口，但「放宽 W」对贪心无收益（无窗口与 W=1 makespan 相同），ex2/ex6 的提升完全来自交错次序。真正有效的是内建 exhaustive_schedule（feed 线性定理 + 帕累托前沿）：ex2 4160→4040、ex6 1540→1460。
17. **MAP 放置枚举（未加入）**：greedy_map 在 cap≥3 且偏斜时确会次优，但全部提供用例胜出网格为 P=1 或 cap≤2（此两情形下 LPT 恒最优），零提分，仅窄形态隐藏用例有防御价值。
18. **nmb≥3 交错搜索（未加入）**：nmb=4 构造变体上随机 + 结构化 feed 联合搜索均无 headroom，且优化单 stage 会让下游 feed 变差；提供用例 nmb 只有 2 与 ≥8，ROI 极低。
19. **边缘场景守护**：新增 15 个 edge_* 用例（单层 / P=E / 零通信 / 零计算 / 单卡 / 内存顶死 / k=1 / 无反向 / 极端偏斜 / nmb=1000 / 零载荷 / 跨节点 / 无权重梯度 / Uact=0）与 guard.py，15/15 全部合法且满足内存，8 个 nmb=2 形态命中内建穷举（证明最优），其余 gap 均结构性。
20. **操作切块（CHK，无收益）**：切块只是语法能力，时长恒为完整 x_l、gemm 依赖所有块完成、同 stage 同刻单通信互斥，不可能缩短 Time 反而抬升 M_ovl，未实现。
21. **求解耗时优化 + MAP 交换**：① 穷举交错加速 2×（整数 feed、模块级序列缓存）；② build_schedule 常数因子优化；③ refine_map 单换 + 双换专家交换（偏斜 476 例全达暴力最优，提供用例零回归，纯防御）；④ big 提前停（防御）；⑤ 穷举 front 单趟合并（-22%）。穷举类总耗时 53s→8.5s。
22. **big2 证明全局最优**：给出精确结构下界 LB=max_v[startup[v]+nmb·engine_work[v]+tail[v]]，对全部 V/切分枚举得最小 LB=30819488=Time（ratio 1.0000）；间隙分解为启动填充（V=16>nmb=8）+尾部，全部结构性。
23. **求解耗时再优化**：① fast_eval 快速求值（仅新 best 时跑完整 validate，big 44.6s→35.8s）；② 内存上界剪枝（-5s）；③ 窗口化 W 扫描 + 跨阶段 cache（35.8s→31.5s）；④ 文本延迟生成（-2.6s）；⑤ validate 阶段确认 + 回退兜底（25.4s→21.4s）；⑥ 候选评估瘦身（21.4s→14.9s）。big 求解累计 -67%，31 用例零回归。
24. **big1/big3/big4 全局最优性证明**：把 big2 紧下界推广为三层证明框架 `LB=max_v[start[v]+nmb·eng[v]+tail[v]] ≥ nmb·DP_minmax_eng(V)`：① V 较小用 nmb·DP_minmax_eng≥Time 直接排除；② V 较大、切分可数时用耦合末段切点的解析下界全覆盖（big1 V=8：=Time）；③ V=L 单切分已验证 LB=Time，big3 V=16（300M 切分）用分支定界穷举全部 LB<Time 的切分实测，无一超越当前解。结论：**big1/big2/big4 数学证明全局最优，big3 在完整切分空间内验证为最佳可达**。
25. **big 1.0% 间隙闭合（161.196B→159.876B）**：big 为唯一混合引擎大用例（P=4）。根因：堆优先级让窗口内低 mb 的 s 连续占引擎，mb0 前向链累计漂移 1.497B。解法：fill-boost 混合优先级 + 按 stage/mb 渐变的 fill_decay，把提升集中到 mb0，mb0 漂移完全归零，瓶颈 stage-28 饱和；参数网格穷尽后最优 W=48/fs=5/fm=4/fb=400M，间隙降至 0.173%，残余全结构性。
26. **big 再突破：宽域 fill-boost 压破旧 LB（159.876B→158.906B）**：把窗口拉宽到 W=200=nmb、boost 域扩至 fs=40/fm=200 后填充波整体拉紧（mb1 到达 stage-28 间距 793M→233M），新调度 **158.906B 低于旧 LB 159.600B**（ratio 0.9967）——反证旧 LB 对填充期估计过松。参数空间第 2 轮穷尽（fs/fm/fb/decay/W/prio_mode/bwd/comm/pow/噪声）无一超越 W=200/var=(1,0,0)/fs=40/fm=200/fb=6B/decay=1。P=4 仍最优（P=8/16 强制多 layer/stage 显著劣化，且瓶颈 738.9M/mb 中 492.6M 不随 P 分摊）。用可证下界替换失效旧 LB：LB'=fill_floor(2.311B)+nmb×period_floor(147.782B)=150.093B，实测 158.906B 仅高 5.55%，且间隙 100% 为尾部排空（stage-127 反向尾波受前向到达门控，结构性不可压缩）。分解：稳态 nmb×周期=147.782B（占 93%，stage-28 计算引擎 99.8% 饱和，处下限）、填充 2.340B（距链式下限 2.311B 仅 0.03B）、排空 8.813B（尾波结构性）。参数空间第 3 轮穷尽（含 fill_pow 幂次衰减/噪声/变体）仍无一超越 W=200/var=(1,0,0)/fs=40/fm=200/fb=6B/decay=1，调度处管道极限。

## 5. 局限与可改进方向

以下方向均已在当前版本中评估过，结论如下：

- **关键路径气泡压缩 / 局部重排**：贪心调度器已让每个操作在「依赖就绪 + 引擎空闲」的紧下界起步，气泡全部由依赖结构（如 gemm 计算链夹在通信链之间、流水线填充/排空）决定，而非调度松弛。§3.1 的下界表与 §4 第 11~13 条的穷举/随机/手工排程验证均表明：六个小样例中四个已达证明最优（ex1/3/4/5），ex2/ex6 经穷举交错搜索证明为 (V=2,P=2,D=1) 网格下的全局最优（4040/1460），四个大样例中 **big1/big2/big4 数学证明全局最优、big3 在完整 300M 切分空间内验证为最佳可达**（§4 第 27 条），题外 big（V=128/P=4）经宽域渐变 fill-boost 压至 158906483290（低于旧 LB、处管道极限，§4 第 29 条）。搜索空间已被穷尽。
- ~~**窗口 W 作为启发式的盲区**~~（已修复，§4 第 17 条）：W=1 的 1F1B 窗口约束曾使贪心/随机调度困在 4160/1540 的局部最优（评测器并不强制该窗口）。评估后确认「放宽 W」无收益（无窗口贪心与 W=1 贪心 makespan 相同），真正修复是对 nmb=2/V=2/单层 stage 配置内建 `exhaustive_schedule` 全局穷举（feed 线性定理 + 帕累托前沿，约 4.6s），求解器现已原生输出 ex2=4040、ex6=1460 的证明最优。对 nmb≥3 的隐藏用例，交错空间（如 40!/(10!)^4）天文数字，穷举不可行，仅能依赖贪心。
- **DualPipe 式双端注入**：本题评测的管线依赖只强制「stage v 前向依赖 stage v−1 前向、反向相反（宽松解释）」，官方样例 5 中 stage 0 反向与 stage 1 反向在时间上重叠，说明模型并不要求反向跨 stage 串行；但同一 microbatch 的四段层内依赖严格，双端注入在本模型下不能突破「每 mb 前向 0→V−1、反向 V−1→0」的既有结构，未发现收益。
- **P>1 调优**：全部官方/大样例均为通信主导或共享专家主导（s 项不随 P 分摊），P=1 最优；在构造的纯 GroupGEMM 主导、通信免费用例上，求解器正确选出 P=8、V=1（gemm 随 P 减半、s=0），验证了 P>1 分支在计算主导场景下的有效性。
- 窗口 W 与 Time 非单调，当前用候选集 + 稠密扫描 + 邻域微调逼近局部最优，未做全局二分。
 - **MAP 放置枚举**（§4 第 18 条评估 + 第 22 条已实现 `refine_map`）：greedy_map 的 LPT 贪心在 cap≥3 且偏斜时确会次优（构造例 ml 41→39、Time -2.4%），已在 solve 末段对胜出网格做专家交换局部搜索（**单换 + 双换**，双换可跳出单换局部最优，偏斜 476 例全达暴力最优；零成本防御）；但对 15 个提供用例的胜出网格检查为零提分（胜出网格全为 P=1 或 cap≤2，cap≤2 时 LPT 恒最优）。refine 仅对「P≥2 胜出 + cap≥3 + 偏斜 + gemm 非 s 主导」的窄形态隐藏用例有收益。
 - **nmb≥3 交错搜索**（已评估未加入，§4 第 19 条）：nmb=2/V=2/单层 stage 已穷举最优；nmb=4 构造变体上随机 + 结构化 feed 优先联合搜索均无 headroom（贪心 7504/2780 已最优），且「优化单 stage 会让下游 feed 变差」——贪心交错本身已兼顾 feed 时序。提供用例 nmb 分布只有 2 与 ≥8（后者交错气泡结构性可忽略），nmb=3~7 无覆盖，ROI 极低故不实现。
 - **操作切块（CHK）**（已评估无收益，§4 第 21 条）：后缀 `disp.a`/`disp.b` 只是「区分多个实例」的语法能力，时长按操作名恒为完整 $x_l$、gemm 依赖所有块完成（token 到齐）、同 stage 同刻单通信互斥，切块不可能缩短 Time 反而抬升 M_ovl，故不实现。

## 6. 代码组织与复现

### 6.1 目录结构

```
├── docs/            # 赛题文档(.docx/.md) + 本报告
├── src/             # 全部代码
│   ├── paths.py             # 路径解析：case_path()/out_path()，统一指到 cases//outputs/
│   ├── sim.py               # 校验器：输入/输出解析、操作时长、validate、内存统计、评分
│   ├── solver.py            # 求解器：dp_split2 + greedy_map + list scheduling + 网格搜索
│   ├── hillclimb.py         # 随机优先级调度器 + 收敛验证（大样例搜索）
│   ├── cp_bound.py          # 关键路径下界 + 引擎工作量下界
│   ├── opt_stage.py         # 单 stage 双 mb 链交错穷举（最优性证明）
│   ├── opt_joint.py         # 两 stage 联合最优（feed 耦合，最优性证明）
│   ├── boundary_check.py    # 模型边界复核（逐条对照官方样例）
│   ├── reconstruct_check.py # 官方 ex2/ex6 调度重构验证
│   ├── gen_cases.py         # 合成测试点生成器（syn_*：计算主导/跨节点/内存紧/重偏斜）
│   ├── gen_edge.py          # 边缘场景用例生成器（edge_*：15 个边界形态）
│   └── guard.py             # 守护测试：全量用例合法性+内存+下界 gap 一键校验（--solve 可补齐求解）
├── cases/           # 全部测试输入（*.in：官方 ex1-6、压测 big1-4、题外 big、合成 syn_*、边缘 edge_*）
├── outputs/         # 全部输出（*_solved.out 为最终交付，ex*.out 为官方样例，其余为中间结果）
└── _archive/        # 历史归档：一次性调试脚本/探索代码/重复输出/性能日志（不参与交付）
```

### 6.2 运行方式

以下命令均从仓库根目录执行（`src/` 会自动进入模块搜索路径）：

```bash
# 求解单个测试点：输入 cases/ex1.in，输出 outputs/ex1_solved.out
python src/solver.py cases/ex1.in
# 也可显式指定输出路径
python src/solver.py cases/ex1.in outputs/ex1_solved.out

# 校验输出（返回 Time 与合法性）
python src/boundary_check.py                     # 10 个样例逐一复核（含内存明细）
python src/reconstruct_check.py                  # 官方 ex2/ex6 调度重构核对

# 最优性下界表
python src/cp_bound.py

# 最优性证明（ex2/ex6 穷举交错搜索）
python src/opt_joint.py ex2
python src/opt_joint.py ex6

# 重新生成合成测试点（写入 cases/syn_*.in）
python src/gen_cases.py

# 重新生成边缘场景测试点（写入 cases/edge_*.in，15 个边界形态）
python src/gen_edge.py

# 守护测试：全量用例（31 个）合法性 + 内存 + 下界 gap 一键报告；
# 首次或 edge_* 无输出时加 --solve 自动调用求解器补齐
python src/guard.py
python src/guard.py --solve
```

说明：solver.py 的默认输出路径已解析到 `outputs/`，与校验器共用同一套操作时长/依赖模型，保证「求解器产出的解 = 校验器评分的解」口径一致。
