## 2. `ex1 = 576`：这 16 个单位从哪来

### 2.1 与题面 §7.1 的时间表对照

题面样例的 20 个操作里，只有 3 个的起始时刻被 solver 改动（其余 17 个完全相同）：

| 操作 | 题面 | solver |
|---|---|---|
| `0:0:s_dw` | 506 | **414** |
| `1:0:gemm_dw` | 460 | **476** |
| `1:0:s_dw` | 576 | **460** |

- **题面**：8 次 AllToAll 首尾相接占满通信引擎 `[16, 576]`（8×70=560），但把 `1:0:s_dw`（时长 16）排在 **576 之后** → 最后完成时刻 576+16 = **592**。题面自己也说"592 已经接近它（通信下界 560）"，但没把最后这个权重梯度塞进计算空隙。
- **solver**：通信引擎仍然 `[16, 576]` **连续无空隙**（我逐区间核对：`disp16-86, disp86-156, comb156-226, comb226-296, comb_bwd296-366, comb_bwd366-436, disp_bwd436-506, disp_bwd506-576`），把 `1:0:s_dw` 前移到 **460**（落在计算引擎的空档里），`1:0:gemm_dw` 排到 476、`0:0:s_dw` 排到 414。于是**计算引擎最晚 500 结束**（`1:0:gemm_dw 476-500`），makespan 由通信下界决定 = **576**。
- 这就是"题面样例 s / s_dw / gemm_dw 的排布空隙"：题面把权重梯度当"尾巴"，solver 把两个 `s_dw` 与 `gemm_dw` 全部塞进计算引擎的空档，只留下通信链当关键路径。净收益 = 16（= 被移走的 `1:0:s_dw` 时长）。

### 2.2 不是取巧

| 检查 | 结果 |
|---|---|
| 操作数 | 20 = 10 op × 2 mb × 1 层，**无缺失、无重复**（judge 与我的复算都确认） |
| 零时长操作 | **一个都没有**（ex1：`s=16, disp=comb=70, gemm=24, s_bwd=16, comb_bwd=disp_bwd=70, gemm_dx=24, gemm_dw=24, s_dw=16`，全部 >0）→ 不可能靠"零时长占位"取巧 |
| 依赖/引擎 | 20 个操作的依赖与两套引擎互斥全部满足（我的独立复算 + judge 双份） |
| 内存 | `groups=(20,2,1) ≤ 39`，与题面一致（Mexp=20、Movl=2U、Mact=1） |
| 最优性 | 见 §5：通信引擎首个操作 ≥16、工作量 560 → `Time ≥ 576`，**solver 的 576 就是下界** → 证明最优 |

## 5. `solver/NOTES.md` 的结构下界复核（F1）

### 5.1 NOTES 的方法与它的漏洞

NOTES §6 的定义是："某卡组某套引擎的**最早开始时刻**（由前驱链决定）加上该引擎在该卡组的**全部工作量**"。
这个下界**有效**，但它**不完整**：引擎的最后一个操作结束后，**同一条依赖链上的后续操作还可能在别的引擎上继续**（例如某 mb 的 `disp_bwd` 之后，该 mb 在另一卡组还有 `comb_bwd → gemm_dx → disp_bwd` 的尾段）。漏掉尾段就会把下界算小，从而误判"还有空间"。

我把两项都算上（尾段取该 mb 在另一卡组上**必须串行**的那一段），得到：

| 用例 | NOTES 结构下界 | 我的下界（含尾段） | solver | 报告目标 | 判定 |
|---|---|---|---|---|---|
| ex1 | 576 = 16 + 560 | **576** = 16 + 560（无尾段） | 576 | 592 | ✅ 达下界 → **最优** |
| ex2 | 4016 = 816 + 3200 | **4832** = 816 + 3200 + **816** | 4880 | 4040 | 差 ≤48；目标 4040 **不可达** |
| ex3 | 4000 = 0 + 4000 | **4000** | 4000 | 4000 | ✅ 最优 |
| ex4 | 3200 = 0 + 3200 | **3200** | 3200 | 3200 | ✅ 最优 |
| ex5 | 384 = 64 + 320 | **416** = 64 + 256 + **96** | 416 | 384 | ✅ 达下界 → **最优**；目标 384 **不可达** |
| ex6 | 1420 = 300 + 1120 | **1736** = 316 + 1120 + **300** | 1744 | 1460 | 差 ≤8；目标 1460 **不可达** |

### 5.2 每一项怎么来的（题面公式手算，全部用 solver 的网格/切分）

- **ex1**：通信引擎首个操作 `disp(0,0)` ≥ `s(0,0)` 结束 = **16**；通信工作量 = `nmb×4×70 = 560` → `Time ≥ 576`。solver = 576 → 最优。
- **ex3 / ex4**：`Fs=0` ⇒ 首个通信操作 ≥ 0；通信工作量 `8×500=4000` / `8×400=3200` → 下界 = 4000 / 3200 = solver → 最优。
- **ex2**（V=2,P=2,D=1）：
  - G1（层 1）首个通信操作 `disp(0,1)` ≥ `s(0,0)`(0) + `disp(0,0)`(400) + `gemm(0,0)`(16) + `comb(0,0)`(400) = **816**；
  - G1 通信工作量 = 8×400 = **3200** → G1 最后一个通信操作 ≥ **4016**；
  - 若最后一个是该 mb 的 `disp_bwd`，其后该 mb 在 G0 的尾段 = `s_bwd`(0) + `comb_bwd`(400) + `gemm_dx`(16) + `disp_bwd`(400) = **816**（若最后一个是 `comb_bwd`/`comb`/`disp`，尾段更长）→ `Time ≥ 4832`。
- **ex5**（V=2,P=1,D=1）：
  - G1（层 1）计算引擎上，两个 mb 的链 = `2×(s16+gemm48+s_bwd16+gemm_dx48) = 256`，首个链操作 `s(0,1)` ≥ **64**（`s(0,0)16+gemm(0,0)48`）→ 最后一条链的 `gemm_dx` ≥ 64+256 = **320**；
  - 该 mb 的 `disp_bwd(1)` 为零时长，随后 G0 尾段 = `s_bwd16 + gemm_dx48 + gemm_dw24 + s_dw8 = 96`（同一台计算引擎，串行）→ `Time ≥ 416`。solver = 416 → **最优**。
- **ex6**（V=2,P=2,D=1）：
  - G1 首个通信操作 `disp(0,1)` ≥ `s(0,0)16 + disp140 + gemm4 + comb140 + s(0,1)16 = **316**`（NOTES 写 300，漏了 `s(0,1)=16`）；
  - G1 通信工作量 = 8×140 = **1120** → 最后一个通信操作 ≥ **1436**；G0 尾段 = `s_bwd16+comb_bwd140+gemm_dx4+disp_bwd140 = 300` → `Time ≥ 1736`。

### 5.3 网格/切分穷举（排除"换个网格就能到报告目标"）

| 用例 | 所有可行 (P,V,D,ψ) 的引擎工作量下界 |
|---|---|
| ex2 | (P=2,V=2,D=1) lb=3200；(P=4,V=1,D=1) lb=**24000**；`V=1,P=2` 因 `Mexp=80>79` 不可行 |
| ex5 | (P=1,V=2,D=1) lb=320；(P=2,V=1,D=1) lb=**1120** |
| ex6 | 只有 (P=2,V=2,D=1) lb=1120（P=1 → `Mexp=80>39`；V=1 → `Mexp=40>39`，都不可行） |

所以 ex2/ex6 的收紧下界适用于**唯一有竞争力的网格**；ex5 的另一网格 lb=1120 > 416。结论不受网格选择影响。

### 5.4 判断：报告目标 4040 / 384 / 1460 不可达，不建议开第二轮

- `4040 < 4832`（ex2 有效下界）、`384 < 416`（ex5 有效下界 = 求解值）、`1460 < 1736`（ex6 有效下界）——**这三个目标都低于有效下界，在题面模型下不可能达到**；不是"搜索不够强"，而是目标本身不成立。`solution-report.md` 的 4040/384/1460 与它在 CONTRACT §8 已被判定为错的 4400/384/1588 同源，不应作为方向。
- 真实剩余空间：ex5 已最优；ex2 最多 48（1.0%，且是否可达未证）；ex6 最多 8（0.5%）。
- 因此：**不建议为这三个目标开第二轮优化**。若仍要榨 ex2/ex6 的最后 48/8，应做的是精确求解（报告 §4 第 17 条的 stage 内双 mb 交错穷举，或 CP-SAT），而不是继续加退火——目前 solver 的退火稳定收敛到题面值，符合"已接近最优"的预期。

## 6. Findings

### F1 · **medium** · `solver/NOTES.md:141-161`（§6 下界证据与"还有空间"的结论）

## 11.2 NOTES §6 逐行复核（我的独立复算）

以本解的实际调度为参照，用题面 §4.2 的依赖与引擎互斥重算：

| 用例 | NOTES 分解 | 我的复算 | 逐项核对 |
|---|---|---|---|
| ex1 | 16 + 560 + 0 | 16 + 560 + 0 = 576 | 首个 `disp` ≥ `s` 16；通信 8×70；L=1 无回落 ✅ |
| ex2 | 816 + 3200 + 816 | 816 + 3200 + 816 = 4832 | 首个 G1 `disp` = 400+16+400；通信 8×400；尾段 `comb_bwd 400+gemm_dx 16+disp_bwd 400` ✅ |
| ex3 | 0 + 4000 + 0 | 0 + 4000 + 0 = 4000 | `s=0`，通信 8×500，单 stage 无回落 ✅ |
| ex4 | 0 + 3200 + 0 | 0 + 3200 + 0 = 3200 | 同上，8×400 ✅ |
| ex5 | 64 + **320** + **32** | 64 + **256** + **96** = 416 | 头段 64 ✅；但 320 是**整个** G1 计算工作量（含旁支权重梯度 2×24+2×8 = 64），而链上工作量只有 2×(16+48+16+48) = **256**；尾段应是 stage 0 的完整回落 `s_bwd 16 + gemm_dx 48 + gemm_dw 24 + s_dw 8 = 96`，不是只算权重梯度的 32 ❌ |
| ex6 | 316 + 1120 + 300 | 316 + 1120 + 300 = 1736 | 旧文档 300 漏 `s(0,1)=16` 已修正；尾段 `s_bwd 16+comb_bwd 140+gemm_dx 4+disp_bwd 140` ✅ |

**为什么 ex5 的 `320 + 32` 不成立**（与它的定义"头段 + 引擎工作量 + 链尾段"对照）：
- `320` = G1 计算引擎的**全部**工作量（`160/µb × 2`），其中 64 是 `gemm_dw/s_dw` 这类**旁支**（只依赖 `comb_bwd`，不在跨卡组依赖链上）；把它们算进"引擎工作量"后，再加"链尾段"就会重复计入链上那部分，并漏掉另一卡组的回落。
- 正确的组合只有两种：
  1. 用**链上工作量**：`64（头段）+ 256（两条 mb 链，2×128）+ 96（G0 完整尾段）= 416`；
  2. 或用"最后一条链完成时刻"论证：两条链共 256、首个链操作 ≥64 ⇒ 最后一条链的 `gemm_dx` ≥ 320，此后该 mb 在 G0 还有 `s_bwd 16 + gemm_dx 48 + gemm_dw 24 + s_dw 8 = 96` ⇒ ≥ 416。
- `320 + 32 = 352` 之所以"碰巧"等于 `256 + 96 = 352`，是因为 ex5 两个 stage 的时长恰好相等（G1 旁支 64 = G0 回落 64）；换一组各 stage 时长不等的用例，这个方法会给出错误下界（可能高到把可行解判成"低于下界"）。
